# 进程与线程

## `task_struct` 在哪里？

!!! question "面试问题"
    `task_struct` 是在进程自己的地址空间里，还是在所有进程共享的内核空间里？

### 我的理解

`task_struct` 是 Linux 内核维护的进程/线程描述结构，位于内核管理的内存中，而不是某个进程自己的用户态地址空间。每个任务都有自己的 `task_struct`，但这些结构都由内核统一创建、访问和管理。

容易混淆的是：**“每个进程都有自己的 `task_struct`”并不等于“`task_struct` 位于这个进程自己的用户空间”。** 前者描述的是对象归属，后者描述的是内存所在的地址空间，两者不是一回事。

!!! warning "我容易答错的地方"
    不要把“每个进程独有 PCB”直接推成“PCB 在进程私有用户空间”。用户态程序不能直接访问内核里的 `task_struct`。

### 和已有知识的连接

- PCB：`task_struct` 可以理解为 Linux 对进程控制块的具体实现之一。
- 内核栈：线程执行系统调用或中断进入内核后，会使用对应的内核栈。
- 调度：调度器通过任务描述结构保存和管理任务状态、优先级以及调度相关信息。

## 进程隔离到底隔离了什么？

!!! question "真实面试 · 2026-08-13 字节跳动多媒体开发一面"
    不同进程之间的资源隔离是怎么实现的？

状态：`[learning] [wrong] [interview]`

### 我当时的理解

我当时抓住了页表这一层：不同进程有各自的地址转换上下文，即使代码里使用相同的虚拟地址，也可以映射到不同物理页，从而实现内存隔离。

但我说过一句过于绝对的话：

> “不同的进程，它访问的肯定是不同的物理地址。”

这是不严谨的。共享内存、共享库、文件映射等场景都可能让不同进程最终映射到同一物理页。

### 现在的理解

我应该把“进程隔离”拆成两层理解：

1. **默认隔离**：每个进程有自己的虚拟地址空间和页表上下文，同一个 VA 不代表同一个 PA。
2. **显式共享**：内核可以有意识地让两个地址空间中的某些页表项指向同一物理页，从而共享数据。

Linux 中内存相关结构不要简单说成“页表直接放在 task_struct 里”，更合适的关系是：

```text
task_struct
    ↓
mm_struct
    ↓
VMA / pgd / page table
    ↓
physical pages
```

进程隔离也不只有内存，文件描述符表、信号状态、凭证等也属于进程资源模型的一部分。

### 易错点

- `[wrong]` “不同进程一定使用不同物理页”——错误，显式共享场景可以共享物理页。
- 不要把“每个进程有自己的 task_struct”和“task_struct 在进程用户空间”混为一谈。
- 面试里如果只说“页表实现隔离”，主干没错，但容易被继续追问共享内存、线程共享地址空间、`mm_struct`。

### 项目连接

`[project]` OS 教学项目：如果简历里写了分页、虚拟内存，就必须能把“每个 task 如何关联地址空间、页表何时切换、共享映射如何例外”说明白，而不是只停留在“VA 转 PA”。

## 共享内存：共享的是物理页，不要求虚拟地址相同

!!! question "真实面试 · 2026-08-13 字节跳动多媒体开发一面"
    共享内存是怎么实现的？

状态：`[learning] [wrong] [interview]`

### 我的理解

我当时已经想到“两个进程最后要访问同一块物理内存”，但又错误地把它说成“两个进程访问相同虚拟地址，再映射到相同物理地址”。

现在更准确的理解是：

```text
Process A: VA 0x400000 ─┐
                         ├─> same physical page
Process B: VA 0x900000 ─┘
```

两个进程的虚拟地址完全可以不同。**共享内存真正共享的是底层物理页，页表分别建立映射。**

### 易错点

- `[wrong]` 共享内存不要求两个进程使用相同 VA。
- 共享内存解决的是“双方能看到同一份数据”，不是“双方如何安全并发访问”。
- “读到一半被写怎么办”属于同步协议问题，需要 mutex / semaphore / futex / ring buffer + 原子索引等机制继续解决。

### 项目连接

`[project]` V853 / 多媒体场景：如果控制消息和大块视频帧分离，可以考虑控制面走 socket、数据面走共享内存；但共享内存一旦引入，就必须同时说明所有权、生产者/消费者同步、覆盖策略和慢消费者处理。

## 2026-10-15 C++ 开发一面：IPC 与线程同步 { #cxx-20261015-ipc-sync }

来源：[C++ 开发岗位一面 · 问题 7～8](../../interviews/2026-10-15-公司未确认-C++开发岗位一面.md#q7-ipc)。状态记为 `[weak] [interview] [project]`。

### 现场暴露

- IPC 只列出有名/无名管道、共享内存、Socket 和 GDBus，没有按数据量、关系、消息边界、拷贝与跨主机能力比较。
- GDBus 被模糊说成“类似 broker 的总线”。更准确地说，D-Bus 是消息总线协议/系统，GDBus 是 GLib/GIO 提供的 D-Bus API；常见 bus daemon 负责名称和消息路由，但也存在点对点连接。
- 线程同步只列 mutex、semaphore、atomic，并说成“保证共享资源不被多个线程并发访问”。同步不仅是禁止并发，还要建立正确的顺序与可见性；并发读可能完全合法。

### IPC 选型不能只背名称

| 机制 | 更适合的关系 | 关键边界 |
| --- | --- | --- |
| 匿名管道 | 有亲缘关系的单向字节流 | 生命周期和 fd 继承，通常半双工 |
| 命名管道 | 无亲缘本机进程的简单字节流 | 打开与阻塞语义，仍无结构化消息模型 |
| 消息队列 | 离散消息 | 容量、消息大小、阻塞与清理 |
| 共享内存 | 大数据/低拷贝 | 最快不等于最简单；必须另做同步和所有权 |
| Unix Domain Socket | 本机双向服务通信 | 支持字节流/数据报、权限与 fd 传递 |
| TCP/UDP Socket | 跨主机或统一网络接口 | TCP framing、UDP 可靠性由应用负责 |
| D-Bus/GDBus | 本机控制面 RPC、信号、属性 | 服务名、对象路径、接口、权限和 bus daemon |

### 同步原语按问题分类

- **mutex**：保护临界区和不变量；不是把整个模块都串行化。
- **rwlock**：读多写少时允许并发读；是否更快需要测量。
- **condition variable**：等待“状态变为满足”，必须在 mutex 保护下循环检查谓词，以处理虚假唤醒和竞态。
- **semaphore**：计数资源或通知可用数量。
- **atomic**：适合简单标志、计数和无锁结构的基础操作；仍要理解内存序，不能替代任意复合不变量的锁。
- **barrier/latch**：让多个参与者在阶段边界会合。

### 和 V853 的关键区分

`cond_new_frame` 是采集线程发布新帧后，通知本地消费者“用户态队列/共享状态有新数据”；`EPOLLOUT` 是内核通知某个 Socket 当前可写。前者解决生产者—消费者条件，后者解决网络 fd 就绪，不能互相替代。

### 推荐口述

> 我不会只按名称背 IPC。小控制消息可用 D-Bus/Unix Domain Socket，D-Bus 上层提供 method、signal 和 property；大块视频数据如果用共享内存，必须同时设计生产者消费者同步和 buffer 所有权。线程内同步也按场景选：mutex 保护复合状态，condition variable 等待条件，semaphore 计数资源，atomic 处理简单状态。同步的目标是建立必要的互斥、顺序和可见性，不是禁止任何并发访问。
