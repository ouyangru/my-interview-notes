# 动态内存分配器

状态：`[weak] [interview]`

## 面试问题

真实面试中被问：

> DSP 子系统地址空间大约只有 1MB，希望实现类似 `malloc/free` 的动态内存分配；申请大小大约集中在 100～400（原始转写单位无法可靠确认），如果让你设计，你会怎么做？

来源：[2026-08-13 字节跳动 · 多媒体开发一面](../../interviews/2026-08-13-字节跳动-多媒体开发一面.md)

## 我当时的理解

当时我没有识别出这是一个“在固定内存池上设计 allocator”的题目，第一反应反而去确认是不是多个进程共享这块内存。面试官明确说只考虑一个进程后，我仍然没有形成方案，最后基本回答“没有思路”。

这说明我之前的“内存管理”学习主要集中在：

```text
虚拟地址 -> 页表 -> 物理地址
```

但没有下沉到：

```text
已经有一块可用内存
        ↓
怎么记录哪些区域空闲
        ↓
怎么分配 / 释放
        ↓
怎么处理碎片
```

## 现在的理解

### 1. 先确认题目到底问哪一层

这类题不是首先讨论 MMU、页表或多进程，而是：

> 已经给你一块原始内存，怎么在这块内存内部实现自己的 `malloc/free`？

更有效的确认方式应该是：

> “我确认一下：这 1MB 是已经给我的、可以直接管理的一块连续内存，我只需要在这块内存内部实现 malloc/free，不考虑进程隔离和虚拟内存映射，对吗？”

### 2. 最简单方案：memory pool + free list

把整块 1MB 当成一个 memory pool。一开始只有一个空闲块：

```text
[---------------------- free 1MB ----------------------]
```

用 free list 记录当前所有空闲区间。

最简单的 metadata 可以理解成：

```c
struct Block {
    size_t size;
    struct Block *next;
};
```

free list 的节点甚至可以直接嵌在被管理的内存中，不需要再递归调用 `malloc()` 创建节点。

### 3. malloc：找 + split

假设找到一个 1000B 的空闲块，但只申请 300B：

```text
1000B free
    ↓ split
300B used + 700B free
```

`malloc()` 返回的是用户可使用区域的首地址，不是 fd。

如果 metadata 放在用户块前面：

```text
[ header ][ user memory ]
          ↑
       malloc 返回这里
```

### 4. free：找回 metadata + merge

`free(ptr)` 只传一个指针，但 allocator 可以通过块头 metadata 找回这块的大小。

释放后如果相邻块也空闲：

```text
[ free 300 ][ free 700 ]
          ↓ merge
       [ free 1000 ]
```

### 5. 碎片

外部碎片：总空闲量够，但没有足够大的连续块。

```text
free 200 | used | free 200 | used | free 200
```

总 free = 600，但一次申请连续 500 仍可能失败。

内部碎片：为了按固定规格分配，实际给出的块大于用户申请大小。

```text
request 260
actual block 512
```

中间浪费属于内部碎片。

### 6. 请求大小长期集中时：size class

如果题目明确申请尺寸长期集中在很窄的范围，例如 100～400，可以按真实分布设计几个 class：

```text
128 class -> free list / bitmap
256 class -> free list / bitmap
512 class -> free list / bitmap
```

优点：分配/释放快、延迟更稳定。

缺点：存在内部碎片，需要根据真实分配分布设计 class。

### 7. buddy 不是“malloc 的唯一正确答案”

buddy 的核心规则是块大小按 `2^n` 管理，大块不断二分：

```text
1024
 ↓
512 + 512
      ↓
   256 + 256
          ↓
       128 + 128
```

释放时，如果自己的 buddy 也空闲，就可以逐级向上合并。

优点：split / merge 快，连续块管理清晰。

缺点：请求尺寸不是 2 的幂时容易产生内部碎片。

所以 DSP 题里如果请求尺寸非常集中，`size class + free list/bitmap` 可能比直接套 buddy 更自然。

## 我目前最容易混淆的点

- `[weak]` “这块内存已经被分配”不是 CPU 自动知道，而是 allocator 的 metadata/free list 已经把它标记为 occupied，并保证后续不会重复分配。
- `[weak]` `malloc()` 返回的是可用内存首地址（指针），不是文件描述符。
- `[weak]` `free(ptr)` 不传 size，是因为 allocator 自己保存 metadata。
- `[weak]` `head = (struct Block *)pool` 不是“又分配了一个 Block”，只是把 `pool` 的起始地址按 `Block*` 类型解释；原始存储空间早已存在。
- `[weak]` `head->next = NULL` 中占用 8B（在常见 64 位系统上）的原因是 `next` 的类型是指针，而不是因为 `NULL` 本身天然占 8B。
- `[weak]` free list 的节点、split/merge 本质上仍然是 C 指针和链表操作，当前链表插入/删除还不够熟练。

## 和 FAT 的个人类比

我觉得 allocator 和 FAT 有一点结构上的相似性：

```text
真实资源 + 一套额外 metadata 记录资源占用状态
```

- FAT：cluster + FAT 表，记录 cluster 是否空闲以及链关系。
- allocator：memory block + header/free list/bitmap，记录哪块空闲、大小以及链关系。

这个类比只帮助理解“管理真实资源需要额外元数据”，不能把 FAT 的非连续 cluster 链和连续地址空间 allocator 当成完全相同的问题。

## 代码练习连接

目前正在用 LeetCode 2502 `Design Memory Allocator` 强行改写 free-list 版本。

当前模型：

```c++
struct Block {
    int start;
    int size;
    Block *next;
};

Block *head;
unordered_map<int, vector<pair<int,int>>> allocated;
```

训练目标不是刷题通过本身，而是理解：

```text
找空闲块
 -> 从左侧切出去
 -> 更新 free block
 -> free 后按地址插回链表
 -> merge 相邻区间
```
