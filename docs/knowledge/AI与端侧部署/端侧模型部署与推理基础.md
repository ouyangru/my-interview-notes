## LLM 与传统 CV 模型不能只按架构一刀切 { #llm-与传统-cv-模型不能只按架构一刀切 }

现场回答用了“LLM 是 Transformer/生成，传统 CV 是 CNN/分类检测”的典型对比，方向不算错，但不是严格定义：

- 现代视觉基础模型也可以使用 Transformer；
- CV 也有生成模型，语言模型也可以承担分类任务；
- “大模型”更重要的特征通常是规模化预训练、较强通用性和通过 prompt/微调等方式适配多任务；
- 传统任务模型通常目标、输入输出和部署形态更固定，但具体资源开销仍取决于结构，而不是名称。

端侧差异更应落到可测对象：

| 维度 | 大模型常见压力 | 传统 CV 模型常见压力 |
| --- | --- | --- |
| 权重/激活 | 权重更大，激活和临时工作区也可能很大 | 通常更小，但高分辨率特征图也可能占大量内存 |
| 运行时状态 | 自回归 LLM 还涉及 KV cache、上下文长度和逐 token 解码 | 常见分类/检测/分割多为一次前向，状态更固定 |
| 算子/shape | 动态 shape、注意力和长序列优化更突出 | resize、卷积、后处理、NMS 等算子适配常见 |
| 指标 | 首 token 延迟、每 token 延迟、吞吐、峰值内存 | 端到端帧延迟、FPS、精度、峰值内存 |

面试时可先说：**不能只按 Transformer/CNN 分，先看训练范式、任务通用性和端侧资源形态。**

## GPU 与 NPU：部署时真正要比较什么 { #gpu-与-npu-部署时真正要比较什么 }

### GPU

- 高吞吐并行处理器，适合矩阵、向量和大规模数据并行；
- 可编程性、算子生态和调试工具通常更通用；
- 不只是“做简单运算”，也不能脱离模型和数据搬运直接说一定比 CPU 快。

### NPU

- 面向神经网络张量算子和常见低精度计算做专用优化；
- 在支持良好的模型上，端侧能效和性能通常更有优势；
- 更依赖芯片厂商的转换器、编译器、算子库和运行时；
- unsupported op、动态 shape 或特殊后处理可能回退 CPU，抵消峰值算力优势。

### 实际选型不能只看 TOPS

至少比较：

1. 模型算子覆盖，哪些层真正落到加速器；
2. 精度类型和量化策略，FP32/FP16/INT8 是否支持；
3. 主机与加速器之间的数据搬运和内存带宽；
4. 编译时间、运行时内存、动态 shape 与 batch；
5. 端到端延迟，而不是只测网络核心部分；
6. 调试工具、部署生态、功耗和稳定性。

## ONNX 是中间表示，不是万能目标格式 { #onnx-是中间表示不是万能目标格式 }

更准确的理解是：ONNX 用计算图、算子和权重表达模型，常作为不同训练框架与推理后端之间的中间表示。典型链路是：

```text
PyTorch
  → ONNX
  → ONNX Runtime（直接运行）
  或
  → 厂商转换器 / 编译器
  → 芯片专用模型格式
  → 厂商运行时
```

并不是所有平台都必须经过 ONNX，也不是有 ONNX 文件就一定能在任意 NPU 高效运行。

### 导出与转换常见卡点

- opset 与算子版本不匹配；
- 自定义算子或控制流不被后端支持；
- 动态 shape / 动态 batch 受限；
- 前处理、后处理未计入模型，设备端实现不一致；
- 布局 NHWC/NCHW、颜色通道、归一化参数不一致；
- 量化后某些层误差放大；
- 转换成功但部分算子 CPU fallback，端到端反而变慢。

### 不能只验证“能跑”

转换前先保存可比较基线：固定输入样本、输出张量、任务指标和 PC 端延迟。转换后逐层次验证：

1. 用同一输入比较原框架与 ONNX 输出；
2. 再比较 ONNX 与目标运行时输出；
3. 出现偏差时先查预处理/后处理，再查算子实现和量化；
4. 在目标设备做 warm-up 后测 P50/P95 延迟、吞吐和峰值内存；
5. 对真实数据集做精度回归，不只比较一张图；
6. 进行长时间运行，观察内存增长、温度和降频。

## 量化不是“模型变小”一句话 { #量化不是模型变小一句话 }

量化通常把权重和/或激活从 FP32 降到 FP16、INT8 等更低精度。它可能减少模型大小、内存带宽和计算开销，但收益取决于硬件和算子实现。

- PTQ：训练后量化，成本低，需要有代表性的校准数据；
- QAT：量化感知训练，训练时模拟量化误差，通常精度更稳但成本更高；
- per-tensor / per-channel、对称/非对称、静态/动态量化会影响精度和后端支持；
- 某些敏感层可以保留较高精度，形成混合精度方案。

出现精度下降时不要立刻归因于“INT8 不行”，应检查校准集、预处理、量化范围、异常值、算子实现和输出解码。

## 推荐的最小实战 { #推荐的最小实战 }

目标不是堆一个很大项目，而是获得可验证的完整证据：

1. 选择一个公开、轻量的分类或检测模型；
2. 在 PyTorch 保存固定测试输入、输出和任务精度；
3. 导出 ONNX，用 checker/简化工具确认图结构；
4. 在 PC 用 ONNX Runtime 对齐输出；
5. 再选择一个实际可用的目标：手机、树莓派 CPU、带 NPU 的开发板或厂商模拟/运行时；
6. 做 FP32/FP16/INT8 至少两种精度对照；
7. 记录转换失败或 unsupported op 的真实处理；
8. 输出表格：模型大小、精度、P50/P95 延迟、峰值内存、功耗（可测时）与运行环境；
9. 写清哪些是亲手验证，哪些只是资料理解。
