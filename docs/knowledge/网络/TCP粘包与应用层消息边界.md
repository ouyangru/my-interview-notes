## 我当时的理解

我当时能抓住主干：TCP 是流式传输协议，不能保证一次发送对应一次接收，所以接收端可能看到多个应用层包粘在一起，也可能只读到半个应用层包。解决思路是在应用层申请缓冲区，并根据应用层协议头里的 magic、版本号、消息头大小、消息体大小来判断是否收到完整消息。

## 易错点

- `[learning]` 我当时把粘包原因说成“TCP 会倾向于把发送缓冲区填满再发送”，这个说法不够严谨。TCP 的发送行为会受到 Nagle、MSS、拥塞窗口、接收窗口、系统调度等因素影响，不能简单理解为“填满才发送”。
- `[learning]` 我当时把拆包说成“包太大，比发送缓冲区大”，这个也不完整。应用层一次 `send()` 的内容可能被 TCP 分段，也可能接收端一次 `read()` 只读到部分字节；关键不是“TCP 包太大”，而是 TCP 不保留应用层消息边界。
- 面试里应该避免说“TCP 包”来指应用层消息，最好说“应用层消息 / 业务报文 / 协议帧”。

## 推荐理解

TCP 只提供可靠、有序的字节流，不提供应用层消息边界。因此，一次 `send()` 不一定对应一次 `recv()`；一次 `recv()` 也不一定得到一个完整业务报文。

应用层要自己做 framing，常见方式包括：

1. 固定长度消息；
2. 特殊分隔符；
3. length-prefix，也就是固定包头 + body length；
4. TLV 或更复杂的协议格式。

在我自己的 TBox MSD 上报场景里，更适合用“固定包头 + body_len”的方式。接收端维护一个应用层接收缓冲区，每次从 socket 读到数据后追加进去，然后循环解析：如果不够包头长度，就继续等待；如果够包头，就解析 body_len；如果完整报文已经到达，就取出一包处理，并把剩余字节留在缓冲区；如果 magic 不对，就做错误恢复或断开连接。

## 推荐口头回答

TCP 是面向字节流的协议，它只保证字节可靠、有序到达，但不保留应用层消息边界。所以发送端一次 send 的数据，在接收端可能被一次 read 读到一半，也可能多个应用层消息被一次 read 一起读出来，这就是我们常说的粘包和拆包。

解决方法一般是在应用层协议里自己做 framing。比如定义固定包头，包头中包含 magic、version、header_len、body_len、cmd、checksum 等字段。接收端维护一个应用层接收缓冲区，每次 read 到数据后先追加到缓冲区，然后循环解析：如果当前长度不够一个包头，就继续等；如果够包头，就解析 body_len，判断完整包是否已经到达；如果完整，就取出这一包处理，并把剩余字节留在缓冲区继续解析；如果 magic 不对，就做错误恢复或者断开连接。

这样无论底层 TCP 怎么分段、合并，应用层都能根据协议头恢复自己的消息边界。
