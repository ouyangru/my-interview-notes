## 我的现场问题

我现场经常先介绍模块功能或项目背景，比如远程控制可以开空调、开车门，语音通话是 eCall / MSD 上传，V853 是网页访问板端摄像头。问题在于面试官真正想听的是：

1. 出了什么问题；
2. 我如何定位；
3. 根因是什么；
4. 我做了什么修改；
5. 结果如何；
6. 我从中复盘出什么工程经验。

如果我先讲大量背景，面试官会觉得我没有抓住问题重点，甚至会怀疑我只是参与过功能，没有独立解决过核心问题。

2026-06-25 速腾聚创一面里，这个问题再次出现。voice core 反复重启本身是一个很好的工程故事：现象明确，定位路径有 crash 文件和调用栈，根因涉及中文文件名解析与 dev / 稳定分支差异，方案也能区分临时清理文件和长期合入修复。但现场表达先花了大量篇幅解释硬件开关、eCall、MSD 背景，导致真正的“问题—定位—根因—方案”出现得太晚。

## 固定表达模板

以后讲 bug / 项目困难，尽量用这个模板：

> 背景一句话 → 现象一句话 → 定位三句话 → 根因一句话 → 解决一句话 → 复盘一句话。

不要一开始讲业务百科，也不要只说“我加日志解决了”。日志只是手段，不是故事本身。

## TBox 可复用故事 1：麦克风故障未上报 DTC

**推荐口头回答：**

我遇到过麦克风故障没有上报 DTC 的问题。现象是测试工具已经模拟出麦克异常，但平台侧没有收到对应故障码。我先在设备监测模块的周期检测、故障成熟条件判断、DTC 上报入口分别加日志，发现前面的状态检测和故障成熟逻辑都正常，问题出在最终上报前的条件过滤。

继续查依赖关系后发现，麦克故障上报依赖麦克使能状态，而这个状态又依赖电源管理模块同步过来的配置。当时对应配置没有正确加载，导致上报条件一直不满足。最后我修改配置后，麦克故障可以正常成熟并上报 DTC。

这个问题让我意识到 TBox 里很多故障不是单模块代码错误，而是模块间状态依赖、配置同步和上报条件共同导致的，所以排查时要按链路分层验证。

## TBox 可复用故事 2：voice core 反复重启

**推荐口头回答：**

语音通话模块里，我参与过基于 TCP 的 MSD 上报协议开发和联调。比较典型的问题是代码刷入稳定版本后，voice core 进程反复重启。我先看崩溃信息和调用栈，发现崩溃点不是 TCP 收发，而是在 voice 进程启动阶段解析板端日志文件的函数。

继续对比分支后发现，开发用的 dev 分支已经修复了中文文件名解析问题，但测试机构要求使用的稳定分支没有合入该修复，所以板端存在中文日志文件时会触发解析异常。临时处理是清理中文日志文件，保证联调继续；长期方案是统一开发、测试和交付分支，或者把解析修复合入稳定分支。

这个问题让我意识到，嵌入式项目里不能只盯着自己刚改的业务代码，版本一致性、进程启动依赖和板端历史数据也可能影响联调结果。

**速腾聚创一面后的压缩版：**

我在语音通话模块做 MSD 上报联调时遇到过 voice core 反复重启。这个功能是紧急呼叫触发后，TBox 通过 TCP 应用层协议把最小数据集上报到后台。问题出现后，我先看板端 crash 文件和调用栈，确认崩溃点不是我新增的 TCP 上报逻辑，而是在 voice 进程启动阶段解析日志文件名。继续对比分支后发现，dev 分支已经修复中文文件名解析，但测试用稳定分支没有合入，板端存在中文日志文件时会触发解析异常。临时处理是清理中文日志文件保证联调继续，长期方案应该是把解析修复合入稳定分支，并保证开发、测试、交付版本一致。这个问题让我认识到板端联调不能只盯自己改的业务代码，版本差异、启动依赖和历史文件也会导致进程异常。

## TBox 可复用故事 3：远控认证阻塞车况上报测试

**推荐口头回答：**

远程控制模块里，我遇到的是一个测试链路被认证流程卡住的问题。当时车况数据上报依赖远控成功态触发，但测试板端没法完成完整认证，所以远控请求无法进入成功分支，后续车况数据上报也无法验证。

我先梳理远控请求从后台模拟工具到 TBox 状态判断、再到车况上报触发的链路，确认上报逻辑本身可以单独验证，问题在前置认证条件导致测试无法进入目标路径。为了支持联调，我在测试版本中临时把车况上报触发条件从远控成功态中解耦出来，让测试可以验证上报内容和链路；正式版本仍然保留完整认证和状态机逻辑。

这个故事一定要强调“测试版本 / 联调辅助 / 不改变量产逻辑”，否则容易被理解为随意绕过认证和状态机。

## V853 项目表达模板

HR 面可以这样说：

> 这个项目不是实验室任务，是我为了补嵌入式 Linux 和网络编程自己做的。我把普通 C++ 网络服务器迁移到全志 V853 开发板上，让多个客户端可以通过网页访问板端摄像头画面。它锻炼的是嵌入式 Linux、视频采集、网络服务、多客户端并发和板端部署能力，所以和车载嵌入式软件开发是相关的。

技术面可以这样说：

> 整体流程是摄像头通过 V4L2 采集视频帧，板端用 mmap 减少用户态和内核态之间的数据拷贝，然后服务端把采集到的视频数据封装成适合 HTTP 或流媒体传输的格式，再分发给多个客户端。并发处理上，我用 epoll 管理多个客户端连接，用线程池处理连接注册和请求解析。为了避免慢客户端拖慢采集线程，我把采集和发送解耦，给客户端维护发送队列，并设置队列上限；如果客户端长期消费不过来，就丢旧帧或者断开连接，优先保证实时性。

## 易错点

- `[weak]` 不要先讲功能百科。面试官问困难问题时，第一句话应该是“我遇到过 X 现象”。
- `[weak]` 不要只说“我加日志定位”。要说日志加在哪里，排除了什么，最后证明了什么。
- `[weak]` 临时绕过流程的改动必须说明边界，否则容易被理解成破坏正式业务逻辑。
- `[weak]` HR 面不用堆 V4L2/epoll 细节，但要翻译成能力：嵌入式 Linux、网络并发、板端调试、多客户端服务。
- `[weak]` 讲 voice core 重启时，不要从“为什么要用硬件开关”开始讲太久；硬件触发背景一句话足够，核心要尽快进入进程反复重启、调用栈定位、版本差异和修复边界。

## 面试追问

1. 这个 bug 如果让你重新排查，你会怎么更快定位？
2. 你加日志具体加在哪些层？为什么？
3. 这个临时方案和正式方案有什么区别？
4. 如果配置文件问题反复出现，你会怎么防止回归？
5. V853 项目里慢客户端一直消费不过来，你怎么处理？
6. voice core 重启时，你从 crash 文件里具体看了哪些字段？
7. 为什么调用栈显示的崩溃点能帮助你排除新增 TCP MSD 逻辑？
