## 我的现场问题

我现场经常先介绍模块功能或项目背景，比如远程控制可以开空调、开车门，语音通话是 eCall / MSD 上传，V853 是网页访问板端摄像头。问题在于面试官真正想听的是：

1. 出了什么问题；
2. 我如何定位；
3. 根因是什么；
4. 我做了什么修改；
5. 结果如何；
6. 我从中复盘出什么工程经验。

如果我先讲大量背景，面试官会觉得我没有抓住问题重点，甚至会怀疑我只是参与过功能，没有独立解决过核心问题。

2026-06-25 速腾聚创一面里，这个问题再次出现。voice core 反复重启本身是一个很好的工程故事：现象明确，定位路径有 crash 文件和调用栈，根因涉及中文文件名解析与 dev / 稳定分支差异，方案也能区分临时清理文件和长期合入修复。但现场表达先花了大量篇幅解释硬件开关、eCall、MSD 背景，导致真正的“问题—定位—根因—方案”出现得太晚。

2026-09-16 岚图智能驾驶一面中，这个问题再次出现，而且已经属于重复薄弱点：面试官要求举一个通信异常，我只说“服务端数据不符合预期、进行代码调整、具体细节记不清”，没有提供最终根因；介绍 TBench 时从人工测试背景一直讲到 HTTP、ADB、WebSocket，接近四分钟仍未进入飞书 Agent 核心，最终被面试官以“时间有限”打断；数据库优化题也先讲页面业务，再次被提醒“讲核心做的事情”。这说明问题并非单次紧张，而是尚未建立稳定的回答层级。

之后项目题统一先给 40～60 秒骨架：**这是什么 → 我负责什么 → 核心问题/动作 → 量化结果**；只有面试官继续追问时，才展开协议、进程和具体组件。故障题则必须提供：**现象 → 定位证据 → 根因 → 修改 → 验证**，如果具体根因记不清，不能用“调整代码”代替。

## 固定表达模板

以后讲 bug / 项目困难，尽量用这个模板：

> 背景一句话 → 现象一句话 → 定位三句话 → 根因一句话 → 解决一句话 → 复盘一句话。

不要一开始讲业务百科，也不要只说“我加日志解决了”。日志只是手段，不是故事本身。

## TBox 可复用故事 1：麦克风故障未上报 DTC

**推荐口头回答：**

我遇到过麦克风故障没有上报 DTC 的问题。现象是测试工具已经模拟出麦克异常，但平台侧没有收到对应故障码。我先在设备监测模块的周期检测、故障成熟条件判断、DTC 上报入口分别加日志，发现前面的状态检测和故障成熟逻辑都正常，问题出在最终上报前的条件过滤。

继续查依赖关系后发现，麦克故障上报依赖麦克使能状态，而这个状态又依赖电源管理模块同步过来的配置。当时对应配置没有正确加载，导致上报条件一直不满足。最后我修改配置后，麦克故障可以正常成熟并上报 DTC。

这个问题让我意识到 TBox 里很多故障不是单模块代码错误，而是模块间状态依赖、配置同步和上报条件共同导致的，所以排查时要按链路分层验证。

## TBox 可复用故事 2：voice core 反复重启

**推荐口头回答：**

语音通话模块里，我参与过基于 TCP 的 MSD 上报协议开发和联调。比较典型的问题是代码刷入稳定版本后，voice core 进程反复重启。我先看崩溃信息和调用栈，发现崩溃点不是 TCP 收发，而是在 voice 进程启动阶段解析板端日志文件的函数。

继续对比分支后发现，开发用的 dev 分支已经修复了中文文件名解析问题，但测试机构要求使用的稳定分支没有合入该修复，所以板端存在中文日志文件时会触发解析异常。临时处理是清理中文日志文件，保证联调继续；长期方案是统一开发、测试和交付分支，或者把解析修复合入稳定分支。

这个问题让我意识到，嵌入式项目里不能只盯着自己刚改的业务代码，版本一致性、进程启动依赖和板端历史数据也可能影响联调结果。

**速腾聚创一面后的压缩版：**

我在语音通话模块做 MSD 上报联调时遇到过 voice core 反复重启。这个功能是紧急呼叫触发后，TBox 通过 TCP 应用层协议把最小数据集上报到后台。问题出现后，我先看板端 crash 文件和调用栈，确认崩溃点不是我新增的 TCP 上报逻辑，而是在 voice 进程启动阶段解析日志文件名。继续对比分支后发现，dev 分支已经修复中文文件名解析，但测试用稳定分支没有合入，板端存在中文日志文件时会触发解析异常。临时处理是清理中文日志文件保证联调继续，长期方案应该是把解析修复合入稳定分支，并保证开发、测试、交付版本一致。这个问题让我认识到板端联调不能只盯自己改的业务代码，版本差异、启动依赖和历史文件也会导致进程异常。

## TBox 可复用故事 3：远控认证阻塞车况上报测试

**推荐口头回答：**

远程控制模块里，我遇到的是一个测试链路被认证流程卡住的问题。当时车况数据上报依赖远控成功态触发，但测试板端没法完成完整认证，所以远控请求无法进入成功分支，后续车况数据上报也无法验证。

我先梳理远控请求从后台模拟工具到 TBox 状态判断、再到车况上报触发的链路，确认上报逻辑本身可以单独验证，问题在前置认证条件导致测试无法进入目标路径。为了支持联调，我在测试版本中临时把车况上报触发条件从远控成功态中解耦出来，让测试可以验证上报内容和链路；正式版本仍然保留完整认证和状态机逻辑。

这个故事一定要强调“测试版本 / 联调辅助 / 不改变量产逻辑”，否则容易被理解为随意绕过认证和状态机。

## V853 项目表达模板

HR 面可以这样说：

> 这个项目不是实验室任务，是我为了补嵌入式 Linux 和网络编程自己做的。我把普通 C++ 网络服务器迁移到全志 V853 开发板上，让多个客户端可以通过网页访问板端摄像头画面。它锻炼的是嵌入式 Linux、视频采集、网络服务、多客户端并发和板端部署能力，所以和车载嵌入式软件开发是相关的。

技术面可以这样说：

> 整体流程是摄像头通过 V4L2 采集视频帧，板端用 mmap 减少用户态和内核态之间的数据拷贝，然后服务端把采集到的视频数据封装成适合 HTTP 或流媒体传输的格式，再分发给多个客户端。并发处理上，我用 epoll 管理多个客户端连接，用线程池处理连接注册和请求解析。为了避免慢客户端拖慢采集线程，我把采集和发送解耦，给客户端维护发送队列，并设置队列上限；如果客户端长期消费不过来，就丢旧帧或者断开连接，优先保证实时性。

## 易错点

- `[weak]` 不要先讲功能百科。面试官问困难问题时，第一句话应该是“我遇到过 X 现象”。
- `[weak]` 不要只说“我加日志定位”。要说日志加在哪里，排除了什么，最后证明了什么。
- `[weak]` 临时绕过流程的改动必须说明边界，否则容易被理解成破坏正式业务逻辑。
- `[weak]` HR 面不用堆 V4L2/epoll 细节，但要翻译成能力：嵌入式 Linux、网络并发、板端调试、多客户端服务。
- `[weak]` 讲 voice core 重启时，不要从“为什么要用硬件开关”开始讲太久；硬件触发背景一句话足够，核心要尽快进入进程反复重启、调用栈定位、版本差异和修复边界。

## 2026-09-21 Sharpa 一面：TBench 不要只讲“飞书入口更方便”

这场面试官连续追问：

- 飞书自己就能收发消息，你到底实现了什么？
- 为什么不直接跑测试脚本？
- 是不是所有人都能调用？
- Agent 误识别怎么办？
- 为什么“每个人”都需要跑这些测试？

现场最大问题是把价值压缩成“飞书入口简单、自然语言比较模糊也能识别”，并且说出“所有人都可以调用”。这会让面试官自然怀疑权限、误执行和资源竞争。

以后 TBench 固定先画出职责链：

> 飞书消息 → Bot 事件接收 → 权限/@ 校验 → Agent 只做结构化参数解析 → deterministic validation / 白名单 / dry-run → TBench → 板端执行 → 日志回传 → PASS/FAIL/SKIP 汇总 → 飞书反馈。

强调三个边界：

1. **飞书是 ChatOps 入口，不是测试执行器。**
2. **Agent 是参数解析器，不是可以执行任意 Shell 的 agent。**
3. **授权范围内的研发/测试人员可用，不是公司所有人都可以无条件控制测试设备。**

这个故事真正能体现工程能力的点，不是“接了 AI”，而是把人工测试流程变成了受控的任务下发、设备预检、执行、日志回收和结果反馈闭环。

### 推荐口头回答

> 直接跑脚本当然可以，飞书接入的目的不是替代 TBench，而是提供统一的 ChatOps 控制面。用户从飞书发任务后，服务端先做权限和命令入口校验，Agent 只负责把自然语言变成结构化参数，结果还要经过设备、路径和参数白名单检查以及 dry-run，合法以后才调用 TBench。任务结束后自动收集日志和结果再发回群里。这样开发者不用登录服务器、找设备、记脚本路径和手动收结果，同时也避免 Agent 直接拥有任意执行权限。

## 2026-09-21 比亚迪一面新增：研究与项目 ownership 先讲边界

这场面试说明，ownership check 不只发生在代码项目，也会发生在研究课题。

### 研究课题的四层边界

以后介绍“无线通信 + AI”时先区分：

1. **概念系统**：边缘端获得感知特征，经无线链路传到边缘服务器做 AI 推理；
2. **实验数据**：公开数据集或 MATLAB 仿真，不等于已经搭建真实雷达采集设备；
3. **我的工作**：OFDM 多载波、特征映射、功率分配、波束赋形、PAPR 和推理准确率优化；
4. **没有做的部分**：真实 Wi-Fi/4G/5G 协议栈、Modem、射频硬件和端到端工程链路。

现场先讲了“边缘设备采集 → 无线网络 → 服务器”，直到面试官追问 Wi-Fi 还是 5G，才说明只用信道模型 H。正确顺序应当反过来：先说“这是算法建模，不是真实无线工程”，再讲系统概念。

### 开源项目的四层边界

V853 项目固定按下面顺序：

1. **开源基线是什么**：静态 HTTP 服务器；
2. **我新增了什么**：采集、多客户端分发、流式发送；
3. **平台现成能力是什么**：Sensor/ISP/硬件编码等；
4. **系统拓扑是什么**：板端服务端、PC 浏览器客户端。

ownership 不是“尽量把所有东西说成自己做的”，而是让对方能够快速验证：我对系统整体有理解，同时不会把标准协议、开源框架或硬件能力冒充自己的实现。

## 2026-09-24 鼎阳一面：被问“拿得出来的功能”仍先讲职责

面试官问得很直接：

> “你在这个自动化测试平台中，有没有一个比较拿得出来讲一讲的功能？”

我当时先解释平台由同事建设、自己负责测试用例、使用时会读源码并向维护者提方案，最后才反问是否需要举一个具体问题。面试官此时说“现在先不用”。这说明回答错过了窗口：问题要的是一个代表作，不是岗位职责清单。

### “代表性功能/问题”固定先抛结论

以后听到“拿得出来的功能”“最有代表性的工作”“解决过什么问题”，第一句话必须出现具体对象和结果：

> 我比较适合讲一个 TBench 短任务日志回传不完整的问题。我定位到根因是日志文件创建与 `tail` 监听之间存在时序竞态，并通过预创建日志文件、调整监听顺序完成修复验证。

如果对方允许继续，再展开完整故事：

> 当时部分执行时间很短的测试任务已经结束，但回传的 `run.log` 不完整。这个问题不是稳定复现，所以我先比较长任务和短任务的执行时序，再沿着任务启动、日志文件创建、`tail` 监听和回传链路检查。最后发现监听启动时目标日志文件还不存在；短任务很快结束时，监听没有正确挂到后续创建的文件，导致日志遗漏。我的方案是在任务启动前先创建空的 `run.log`，再启动监听，最后执行测试脚本，同时保留退出状态和完整日志回传。修改后用多组短任务和失败任务回归，日志能够稳定收齐。这个问题让我意识到日志链路也存在进程与文件创建的竞态，不能只看业务脚本是否执行成功。

这段素材来自已有 TBench 复盘，不是本场现场回答。面试复盘中必须明确写成“本来应该答但当时没有展开”，不能把它伪装成当时已经说过。

### 研究课题也要先说“我的问题”

本场研究课题再次出现同一表达模式：先讲摄像头、雷达、降维、边缘服务器和人体动作识别，面试官听到的是“普通网络上传”，于是连续追问协议、接口和优化内容。固定顺序应改成：

1. 结论：OFDM 边缘推理场景下的物理层资源优化；
2. 本人工作：各子载波功率分配；
3. 目标与约束：任务推理性能、总功率、PAPR；
4. 边界：算法仿真，不是真实 Wi-Fi/4G/5G 或 PA 硬件测试；
5. 对方继续追问后，再讲边缘设备、特征和应用示例。

详细技术内容见：[OFDM 高 PAPR 与任务导向功率分配](../计算机网络/OFDM高PAPR与任务导向功率分配.md)。

### “偏内向”问题的素材是够的，但仍要压缩

我现场能够给出三类工作证据：帮助其他实习生使用 Git、理解 TBox 和设计测试用例；发现 TBench 问题后主动整理背景、现象、排查、根因和测试结果；与异地平台维护同事沟通。这些证据比单纯说“我工作时很外向”更可信。

下次压成一句结论加一个例子：

> 我性格确实偏内向，但工作沟通没有问题。在小鹏做 TBench 时，我需要和异地平台同事协作；发现问题后，我会把背景、复现现象、排查证据、根因、方案和验证结果整理好再沟通，也会主动帮助其他实习生解决 Git、TBox 和测试用例上的问题。
