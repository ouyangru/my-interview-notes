## 先建立一个原则：这些协议不在同一层

不要把 SPI / UART / I²C / CAN 和 MQTT / TCP 混成同一类。

- SPI / UART / I²C / CAN：更靠近板级或总线通信；
- TCP：传输层；
- MQTT：应用层协议，通常跑在 TCP 长连接之上。

所以面试官问“数据为什么没到”时，要先确认他在问：

> 板内总线问题、TCP 连接/发送问题，还是 MQTT 业务消息问题？

这和今天 CAN “抢占”答成应用队列是同一种层级混淆风险。

## 一、SPI：面试官不只会问“四根线”

### 高频场景 1：一个 SPI 总线挂三个设备，怎么选其中一个

想考：

- SPI 的主从结构；
- CS / SS 片选；
- 和 I²C 地址寻址的区别。

推荐回答：

> SPI 常见有 SCLK、MOSI、MISO 和 CS。多个从设备通常共享 SCLK、MOSI、MISO，但每个从设备有独立的 CS。主机要和哪个设备通信，就把对应 CS 拉到有效电平，其他设备保持未选中状态。这个和 I²C 不一样，I²C 主要靠地址字段选择从机。

### 高频场景 2：为什么 SPI 往往比 I²C 吞吐高

想考：

- 同步时钟；
- 全双工；
- 协议开销；
- 线数 trade-off。

推荐回答：

> SPI 由主机提供时钟，MOSI 和 MISO 分开，通常可以全双工，而且没有 I²C 那样的地址和逐字节 ACK 开销，所以实现上容易做到更高吞吐。但代价是占用引脚更多，多个从机通常还需要额外 CS。

### 高频场景 3：数据读出来全错，但示波器上有波形

要想到：

- CPOL / CPHA 模式不一致；
- 时钟频率过高；
- CS 时序不对；
- 字节序 / bit order；
- 电气问题。

面试回答不要只说“可能接线错了”，可以说：

> 我会先确认 SPI mode，也就是 CPOL/CPHA，确保主从双方在同一个时钟边沿采样；再看 CS 是否覆盖完整事务、频率是否超过从设备能力、bit order 和字节序是否一致。如果有逻辑分析仪，会直接对照数据手册检查时钟和采样边沿。

### 易错点

- SPI 没有像 I²C 那样统一的“设备地址”机制；
- “四根线”只是典型单从机表述，多从机通常会增加 CS；
- 不要把 SPI 说成天然可靠协议，它本身没有像 TCP 那样的重传/可靠交付语义。

## 二、UART：重点是“没有时钟为什么还能通信”

### 高频场景 1：UART 没有时钟线，双方怎么知道一个 bit 多长

想考：

- 异步通信；
- 波特率；
- 起始位；
- 接收端采样。

推荐回答：

> UART 是异步串口，双方事先约定波特率。线路空闲通常为高，接收端检测到 start bit 后，就按照自己的本地时钟在后续 bit 周期的合适位置采样数据位，最后检查 stop bit。因为双方没有共享时钟，所以波特率偏差过大时采样点会逐渐漂移，最终出现乱码或 framing error。

### 高频场景 2：UART 为什么会乱码

先按层排：

- 波特率不一致；
- 数据位 / 校验位 / 停止位配置不同；
- 电平标准不匹配；
- 丢字节 / 缓冲区溢出；
- 上层帧边界解析错误。

推荐回答：

> 我会先确认最基础的串口参数一致，包括 baud rate、data bits、parity、stop bits；再看接收缓存有没有 overrun。如果底层字节流是对的但业务数据错，再检查上层协议帧头、长度和校验，不会一上来就把所有问题都归因于 UART 本身。

### 高频场景 3：SPI 和 UART 怎么选

推荐回答：

> 同板高速数据交换更常考虑 SPI，因为同步、吞吐高；如果是简单调试口、低速控制、线数和实现复杂度更敏感，UART 更简单。最终还要看现有硬件设计、带宽、距离、是否需要全双工以及驱动支持，不能只按“谁更快”决定。

## 三、MQTT：不要只会说“发布订阅”

### 高频场景 1：为什么 TBox / IoT 常用 MQTT

推荐回答：

> MQTT 是基于 Broker 的发布订阅协议，设备和业务服务通过 topic 解耦，不需要彼此直接维护点对点关系；同时它基于长连接，适合设备状态上报、命令下发和弱网络环境下的持续在线场景。对 TBox 来说，云端可以通过 topic 下发远控或配置，车端也可以按 topic 上报状态。

### 高频场景 2：QoS 0 / 1 / 2 有什么区别

必须至少说到：

- QoS 0：至多一次；
- QoS 1：至少一次，可能重复；
- QoS 2：恰好一次语义，握手更复杂、开销更大。

工程追问：

> 如果远控消息用 QoS 1，重复消息怎么办？

正确方向：

> QoS 1 只能保证至少到一次，不保证业务只执行一次，所以业务层仍然需要 request id / sequence number / 幂等设计，不能因为 MQTT 有 QoS 就认为远控一定不会重复执行。

### 高频场景 3：MQTT KeepAlive 和 TCP KeepAlive 是一回事吗

推荐回答：

> 不是。TCP KeepAlive 是内核 TCP 层的连接探测机制，通常粒度比较粗；MQTT KeepAlive 是应用层协议的一部分，会通过 PINGREQ/PINGRESP 等消息确认 Broker 连接是否仍可用。业务如果还需要知道服务是否健康、登录态是否有效，可能还会有更上层的心跳或状态上报。

### 高频场景 4：MQTT 连接还在，但远控业务失败，怎么查

分层：

> TCP 是否仍连接 → MQTT 会话 / SUB 是否正常 → topic 是否正确 → Broker 是否收到 → payload 是否符合协议 → Linux 业务是否解析 → Linux-MCU → CAN → ECU → ACK/业务响应。

核心是：

> “网络连接活着”不等于“业务执行成功”。

## 四、TCP：最容易从八股追到项目

### 高频场景 1：`send()` 一次是不是一定把 len 全发完

答案：不是。

推荐回答：

> `send()` 返回值表示这一次实际接收了多少字节到内核发送路径，并不保证等于请求长度。非阻塞 Socket 下可能只发送一部分，也可能返回 EAGAIN。应用层要维护 buffer 和 offset；部分发送就从剩余位置继续，EAGAIN 就等 EPOLLOUT 再发送。

### 高频场景 2：`send()` 成功是不是代表业务成功

答案：不是。

固定区分三层：

1. 连接状态；
2. 发送状态；
3. 业务 ACK / 执行结果。

推荐回答：

> TCP send 成功最多说明这部分数据被本机协议栈接受处理，不代表对端业务已经执行。比如远控命令发出后，仍然要等业务层 ACK 或最终 ECU 执行结果。网络发送成功和业务成功不能混为一谈。

### 高频场景 3：为什么 TCP 还有“粘包拆包”

因为 TCP 是字节流，不保留应用层消息边界。

常见方案：

- 固定长度；
- 分隔符；
- header + length + payload；
- 必要时校验字段。

不要说“TCP 把两个包粘在一起是 bug”。更准确是：

> 应用一次 send 和对端一次 recv 不存在一一对应关系，业务层必须自己定义消息边界。

### 高频场景 4：非阻塞 Socket 为什么要配 epoll

推荐回答：

> 非阻塞的目的不是“让 send 更快”，而是避免一个慢连接把线程卡住。调用 send/recv 暂时无法继续时返回 EAGAIN，线程可以去处理其他连接；epoll 用来高效等待哪些 fd 真正可读/可写，事件到来后再继续处理。

### 高频场景 5：EPOLLOUT 是不是一直监听

工程回答：

> Socket 大多数时候通常都是可写的，如果长期无条件监听 EPOLLOUT，可能产生大量无意义唤醒。更常见的做法是：有待发送数据而且当前 send 遇到 EAGAIN 时才关注 EPOLLOUT；队列清空后取消可写关注。

### 高频场景 6：TCP 断线后怎么办

至少分：

- 连接重建；
- 未发送完数据怎么处理；
- 已发但未确认业务 ACK 的请求怎么处理；
- 重试是否会造成重复业务。

推荐回答：

> 连接断开后首先重建连接，但业务不能只做“重连再发一遍”。需要区分消息是否已经发出、是否有 request id、业务是否幂等、ACK 是否已经返回。否则网络重试可能演变成重复执行。

## 五、把这些协议挂回我的项目

### TBox

固定分层：

> 云端 MQTT/TCP → Linux 应用 → SPI/UART → MCU → CAN → ECU。

所以：

- MQTT：云端发布订阅和会话；
- TCP：可靠字节流、连接、partial send、EAGAIN、业务 ACK；
- SPI/UART：Linux 与 MCU 的板内通信；
- CAN：MCU 与车内 ECU 的总线通信和仲裁。

### V853

主要涉及：

- TCP / HTTP：客户端连接和流数据发送；
- epoll / 非阻塞 Socket：多客户端；
- partial send / EAGAIN：持续流发送；
- RTSP/RTP：媒体控制和传输；
- 不要把板级 SPI/UART 问题强行套进 V853 流媒体主链。

## 六、固定训练方式

以后不要只复习“定义”，每个协议至少练这四种问法：

1. **结构题**：几根线 / 哪一层 / 谁和谁通信；
2. **选择题**：为什么用它而不用另一个；
3. **异常题**：数据错、断连、慢、重复、超时怎么办；
4. **边界题**：底层成功为什么不等于业务成功。

下一次模拟优先从场景提问，不直接提示协议名。例如：

> Linux 已经把远控请求发给 MCU，但 ECU 没动作，你怎么判断问题在 TCP、MQTT、SPI/UART 还是 CAN？

如果能先分层再定位，才算真正掌握，而不是只背协议名。
