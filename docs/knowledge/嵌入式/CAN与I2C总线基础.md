## CAN：仲裁到底发生在哪一层

### 我的历史错误

Sharpa 一面里，面试官问 CAN 总线上状态报文一直在发送，如果又来了控制报文，两者如何“抢占”。我现场回答成：

> 可能会存在一个队列，把需要发送的事件放进事件队列，一个一个串行处理。

这回答的是应用层任务排队，不是 CAN 总线仲裁。

### 正确理解

CAN 是多主总线。多个节点在总线空闲时可以同时开始发送，在仲裁字段逐位比较。

- 显性位：0
- 隐性位：1
- 显性 0 会覆盖隐性 1
- 某节点发送 1 却读回 0，说明自己仲裁失败，立即停止发送
- 继续发送的报文获得总线
- 标准数据帧中通常可以粗略记成：**数值更小的 CAN ID 优先级更高**

这个过程是无损仲裁：胜出的帧从头到尾没有被破坏，失败节点等总线空闲后再尝试。

### 面试口头回答

> 如果问的是 CAN 总线本身的抢占，不能只回答应用层队列。多个节点同时发报文时，CAN 会在仲裁字段逐位比较，显性 0 会覆盖隐性 1，所以 ID 更小的报文通常获得更高优先级。仲裁失败的节点停止发送，等下一次总线空闲再尝试。对于实时性或安全性更高的消息，系统设计时会给它更高的报文优先级。
>
> 在我的 TBox 项目里，Linux 应用只把业务请求发送给 MCU，真正 CAN 报文发送和总线仲裁发生在 MCU/CAN 控制器这一侧。

### 易错点

- CAN ID 不是简单的“节点地址”。CAN 更偏消息/报文标识，接收节点根据过滤规则决定是否处理。
- 应用层可以有发送队列，但它解决的是软件调度，不等于 CAN 总线仲裁。
- “优先级高”不能简单理解成操作系统线程优先级。

## I²C：多从机时序

### 我的历史问题

恒玄和 Sharpa 两次真实面试都没能稳定讲出 START/地址/ACK/数据/STOP，因此保持 `[weak]`。

### 两根线

- SCL：时钟
- SDA：数据
- 两根线通常是开漏/开集电极结构，需要外部上拉
- 总线空闲时通常 SCL=1、SDA=1

### 一次典型写操作

1. 主机产生 START：SCL 为高时，SDA 从高变低。
2. 主机发送 7 位从机地址 + 1 位 R/W。
3. 地址匹配的从机在第 9 个时钟拉低 SDA，返回 ACK。
4. 主机逐字节发送数据，每个字节之后等待 ACK。
5. 发送完成后产生 STOP：SCL 为高时，SDA 从低变高。

### 读操作

读操作的 START 和地址阶段类似，只是 R/W 位表示读；随后从机驱动 SDA 输出数据，主机在每个字节后通过 ACK/NACK 表示是否继续读取，最后发 STOP。

### 为什么一根总线能挂多个设备

I²C 不依赖独立片选线，而是依赖从机地址。所有从机都能看到总线上的地址字段，只有地址匹配的从机进行 ACK 并参与后续传输。

### 和 SPI 最容易混淆的地方

- I²C：SCL + SDA，通过地址选设备。
- SPI：SCLK + MOSI + MISO + CS，通过独立 CS 选设备。
- I²C 通常半双工语义、线少、支持多设备寻址；SPI 通常吞吐更高、全双工、每个从机通常要额外 CS。

### 面试口头回答

> I²C 有 SCL 和 SDA 两根线，总线空闲时都被上拉为高。主机开始通信时，在 SCL 为高的时候把 SDA 从高拉低形成 START，然后发送 7 位从机地址加读写位。所有从机都能看到地址，但只有地址匹配的从机在第 9 个时钟返回 ACK。之后按字节传输数据，每个字节后都有 ACK/NACK，最后在 SCL 为高时让 SDA 从低变高形成 STOP。所以多个设备共享一条 I²C 总线时，靠地址区分，不像 SPI 用独立 CS。
