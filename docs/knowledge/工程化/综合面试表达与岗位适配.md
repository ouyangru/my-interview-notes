## 我的理解：先回答问题，再决定讲多深

在英文介绍、项目介绍、缺点、职业规划甚至爱好问题中，我经常先解释背景或自己反复思考的过程，再迟迟给出结论；面试官在爱好题明确说“好，就不用展开”，这是回答长度失控的直接反馈。**不是内容越多越可信，而是要让听的人先知道我想表达什么。**

### 我容易犯的具体错误

1. 问“做了什么”时，先讲原负责人有多忙、项目迁移历史，却没有马上说“我定位了什么、改了什么”。
2. 问“缺点是什么”时，一次讲行业深度、工作焦虑、没理解测试用例三个负面点；其中“没有先想清测试目的”已有后续改进经历，本可以作为唯一主案例。
3. 问“AI 怎么用于网络技术工程师”时，停留在“观察工作痛点、脚本自动化、Vibe Coding”，没有联系**网络产品开通、日志/告警、配置核查、客户关单与风险控制**。
4. 面试官问“服气不服气”，真正要考察的并不是承认输赢，而是我能否用工程目标评价方案、接受证据并与团队合作。

## 改进后的口头习惯

- 简单事实：一句话直接回答。如排名、是否有某项爱好或实习来源。
- 经历项目：**问题现象 → 我的责任边界 → 定位/行动 → 证据和结果 → 风险或局限**。
- 行为面试：**结论 → 真实分歧/压力场景 → 当时行动 → 改变了什么 → 反思与可迁移做法**。
- 工作不确定：先给已知事实，再承认未知；不要为了表现诚恳而叠加不必要的个人负面信息，也不要为了录用虚构自己能接受的驻外安排。

### 现场例子 1：缺点 [weak]

当时说了三个缺点，还提到因为困扰任务而睡眠受影响。后续面试官随即要求举一个更严重的例子，讨论焦点离开了任务结果。

**下次应答**：我过去接到陌生任务时，有时会过快进入实现，没有先理解业务目标。在 TBox 测试任务中，最初只考虑怎么写测试用例，不清楚为什么选择那些模块；后来通过与负责人对齐，了解到它与定制化内核及 TBox 关键模块直接相关。从此接任务先确认背景、验收指标和约束，再确定实现方案。

### 现场例子 2：团队方案分歧 [learning]

我与上海维护测试框架的同事，对设备重启逻辑放在具体测试脚本还是平台控制层存在不同思路。我的第一反应是脚本就近修复；对方指出统一控制更有利于避免重复重启和流程中断。最终我接受对方方案，并认为后续操作体验更好。

**易错边界**：录音没有证明“日志覆盖一定由脚本重启解决”，也不能推断具体实现类、API 或提交已存在；需要回当时日志/工单/代码核对。

2026-10-14 一面英文介绍卡在教育经历；2026-10-20 二面在英文介绍中又出现明显卡顿及中英切换。因此这是**两场重复出现**的临场组织问题，而非单次偶发。但英文词句的 ASR 误识别不等同本人真实发音错误。

## 面试追问与掌握验证

1. 不看稿做一次 90 秒英文介绍，然后随机加问：“Please describe one technical issue you resolved in your internship.” 只有在脱稿和换问法仍流畅时才考虑状态变化。
2. 60 秒回答“你的缺点”，要求只选一个真实例子且必须包含已经采取的改善行动，再换问法考抗压。
3. 90 秒讲“AI 用于海外网络设备开通故障”，要求有现场数据采集、告警分级、安全校验、专家升级、客户确认与回滚边界。
4. 解释 TBench 重启策略为什么不应该由每个测试脚本各自控制，并给出一个反例；若无法核实真实日志与实现，明确讲这是设计讨论而非已验证的故障根因。

## 2026-10-28 贝壳一面：端侧 AI 岗位适配 { #2026-10-28-贝壳一面端侧-ai-岗位适配 }

来源：[贝壳找房嵌入式软件一面 · 问题 3～5](../../interviews/2026-10-28-贝壳找房-嵌入式软件一面.md#q3)。`[weak] [interview]`

面试官不止问“感不感兴趣”，还构造了一个长期场景：同组别人每天都在做我更擅长的 Linux 软件，而我持续做模型转换和端侧落地，能否保持心态。这个追问是在判断：

- 我是否在投递前真正理解岗位；
- 兴趣是否有行动证据，而不只是“方向热门”；
- 入职后会不会因内容不符而转岗或离职；
- Linux 经验能否迁移成端侧系统能力，而不是与模型部署竞争。

现场用“小鹏入职后工作内容变化”和“主动承接数据库优化”证明适应性，这个例子有效；但“我并不介意工作内容”“没有把方向定死”会让职业选择显得被动，且没有任何亲手部署模型的行动证据，所以仍记 `[weak]`。

### 更稳的表达结构

1. **明确选择**：能接受，并理解这是端侧算法部署岗，不是传统 Linux 应用岗；
2. **迁移基础**：Linux、音视频采集、内存和性能排查是端侧落地的基础，不是无关经历；
3. **承认缺口**：模型转换/量化/厂商运行时没有实战，不包装；
4. **给行动证据**：亲手完成一个小模型的 ONNX 与目标运行时部署，而不只说准备学；
5. **长期预期**：希望独立负责一个算法从模型到设备验证的完整闭环。

### 推荐口述

> 我理解这个岗位的核心不是传统 Linux 应用开发，而是模型转换、量化、芯片运行时接入和端侧性能验证。我愿意做这个方向，因为 Linux、音视频采集、内存管理和排障正好可以迁移到模型落地环节；我要补的是算法工具链。小鹏实习中我也经历过从预期的 C++ 应用转到 Python、测试平台和数据库优化，仍能把任务做出结果。现在的不足是没有完整板端部署经历，我会用一个可复现的小项目先补出真实证据。入职后先把本职方向做深，再用系统基础和团队协作解决跨层问题。

状态不因形成这段答案而变化；只有实际部署证据和换问法回测后再评估。
