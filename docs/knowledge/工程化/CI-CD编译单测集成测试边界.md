## 我真实说错的点

速腾聚创这场里，我在解释 CI/CD 流水线时说过类似“如果编译通过了，那么代表我这个代码逻辑上写的是没什么问题”。这个说法需要标 `[wrong]`，因为编译通过只能说明代码能被构建出来，不能证明业务逻辑正确。

后面我补充了 GoogleTest、测试 fixture、Mock 外部依赖、断言和覆盖率，这部分方向是对的，但当时没有把“编译、单测、集成测试、台架联调”四层的边界讲清楚，所以答案容易显得像在背工具名。

## 我的理解

这几个概念要分层讲：

编译 / 构建解决的是“代码能不能变成目标产物”。它检查语法、头文件、依赖、链接、编译选项和构建脚本，但不保证功能正确。

单元测试解决的是“单个模块在隔离条件下是否符合预期”。核心是确定被测对象，Mock 外部依赖，构造输入，用断言或 EXPECT_CALL 验证输出、状态变化、回调和异常分支。

集成测试解决的是“多个模块连起来以后接口和状态机是否能跑通”。它更关注模块边界、真实调用链、协议字段、时序、错误码和异常处理。

台架测试 / 实车联调解决的是“软件放到真实或接近真实环境里是否可用”。它会覆盖板端资源、网络波动、MCU 响应、CAN 报文、日志、固件版本、外设状态和真实链路时序，这些不是单测能完全覆盖的。

## 推荐口头回答

CI/CD 流水线对我来说不是简单地“编译一下”，而是把代码提交后的构建、检查和测试流程自动化。编译通过只能说明语法、依赖和链接层面没有问题，不能代表业务逻辑正确。真正验证逻辑要靠后面的单元测试、集成测试和台架联调。

以 TBox 远控或 MSD 上报模块为例，单元测试阶段我会先确定被测对象，比如报文封装函数、状态处理逻辑或 ACK 回调处理逻辑。对于云端下发命令、MCU 响应、网络发送这些外部依赖，我会用 Mock 或桩函数模拟，然后构造正常输入、超时、连接中断、响应异常等场景，通过断言检查输出报文、状态变化和回调是否符合预期。

但是单元测试只能证明单个模块在可控输入下基本正确。真正放到板端以后，还要通过集成测试和台架测试验证 Linux 业务进程、网络连接、MCU 通信、CAN 侧响应、日志采集和异常处理能否串起来。所以我会把编译、单测、集成测试和台架联调看成不同层次的质量保障，而不是把编译通过等同于逻辑正确。

## 易错点

- `[wrong]` 编译通过不代表代码逻辑正确，只代表构建层面过关。
- `[weak]` 覆盖率不是质量本身。覆盖率高只能说明代码路径被执行过，断言是否有效、Mock 是否真实、边界场景是否覆盖仍然要单独看。
- `[weak]` Mock 不是为了“造假通过测试”，而是为了隔离外部依赖，让单元测试能稳定验证一个模块的输入输出和状态变化。
- `[project]` 台架测试和单元测试不是替代关系。单测偏函数/模块，台架偏真实链路和环境问题。

## 项目连接

- 经纬恒润 TBox：版本提测、台架压测、固件刷写、实车联调可以作为“集成测试 / 台架测试 / 真实环境验证”的项目连接。
- 小鹏 TBench：测试用例、结果判定、异常日志采集、飞书机器人通知可以作为“测试流程自动化和失败可定位”的项目连接。
- 速腾聚创复盘：这道题的核心修正是，不要再说“编译通过说明逻辑没问题”，应该说“编译只是质量门禁的第一层”。
