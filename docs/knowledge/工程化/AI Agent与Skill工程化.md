## 2026-10-15 现场回答与修正 { #cxx-20261015-agent-skill }

来源：[C++ 开发岗位一面 · 问题 17～18](../../interviews/2026-10-15-公司未确认-C++开发岗位一面.md#q17-ai)。

现场已经说出两个正确边界：Agent 可以把自然语言解析成结构化参数；解析结果必须校验并准备兜底。但回答仍然偏“AI 能推理、脚本只能关键词匹配、Skill 自动生成后验收”，没有把权限、确定性执行、幂等、审计和测试讲成完整闭环。

## Agent 不等于让模型直接执行命令

以 TBench 飞书接入为例，可控链路应是：

`飞书消息 → 身份/@/权限校验 → Agent 解析结构化意图 → schema/范围/白名单校验 → 设备预检与 dry-run/确认 → 调用确定性 TBench API → 任务状态与日志 → PASS/FAIL/SKIP 回传`

关键点：

- 模型只处理自然语言不确定性，不拥有任意 Shell 或任意设备控制权限；
- 工具输入有严格 schema、枚举、路径和设备白名单；
- 高风险动作需要明确确认，失败时安全停止或回滚；
- 每个任务有 request/job id，重复消息不重复执行；
- 原始请求、解析参数、工具调用和结果都可审计；
- Python 并不只能做关键词匹配，它负责确定性校验、编排和执行，Agent 只补足语言理解。

## Skill 是可复用任务上下文，不是“自动正确”

一个工程化 Skill 通常固化：

1. 适用范围和触发条件；
2. 必须读取的领域资料、接口和规范；
3. 固定步骤、工具权限和禁止事项；
4. 输入/输出格式与验收标准；
5. 正常、边界和失败示例；
6. 必要的确定性脚本或模板。

Skill Creator 可以帮助生成初稿，但不能证明结果正确。验收至少覆盖：正常任务、歧义输入、缺字段、越权参数、工具失败、重复请求和不可恢复动作。任何“自己测试过”的结论都要能给出具体用例和结果。

## AI 编程的最小闭环

1. 提供真实接口、局部代码、约束和验收条件，不把整个敏感仓库无边界交给模型；
2. 要求小 diff，并人工审查所有权、并发、错误路径和安全边界；
3. 运行格式化、静态检查、单元测试和必要的集成/设备测试；
4. 对性能修改保存基线和对照数据；
5. 保留来源和不确定项，不把模型推测写成已验证事实。

## 推荐口述

> 我在飞书接入 TBench 的场景里，把 Agent 定位成自然语言到结构化参数的解析层，而不是任意命令执行器。解析结果还要经过权限、设备和参数白名单、schema、设备预检，必要时 dry-run 或人工确认，合法后才调用确定性的测试接口；任务要有 ID、日志和幂等处理。Skill 则是把稳定的任务说明、领域规范、工具边界、示例和验收方式复用起来，自动生成只能做初稿，仍要用正常、边界和失败样例验证。

## 2026-10-19 新凯来：Agent、上下文管理和 Shell 安全 { #xinkailai-20261019-ai }

来源：[新凯来技术面 · 问题 4、9～11](../../interviews/2026-10-19-新凯来-岗位未确认技术面.md#q4)。Agent/大仓库上下文记 `[learning] [interview] [project]`，Shell 安全工程化边界记 `[weak] [interview]`。

### 我现场真正讲到了什么

- Agent：表示使用阿里提供的 SDK，不是从零写框架；没有把自己做过的飞书→结构化测试参数→TBench 测试→日志反馈集成边界讲明。
- “web coding”：可能是 ASR 将 Vibe Coding 识别错，转写不能当作确认术语；我说用 AI 辅助 Python 快速开发，未主动补“自己怎么审查/测试”。
- 大仓库：我提出**先索引模块路径、缩小上下文和修改范围**，这个思路正确，但没讲检索真实调用关系、影响面、测试与 diff 检查。
- Shell：我只举 `rm -rf`，防范措施主要是 prompt 规则 + 关键词扫描。这不足以作为安全边界，因为危险行为可能通过变量展开、管道、`dd`、`mkfs`、`git clean -fdx`、`git reset --hard`、`chmod -R` 或其他语言间接执行。

### 我的理解（复盘后，尚未实作验证）

模型应负责不确定的语言理解和候选修改，真正执行权限必须由 **工具执行器** 限制，而不是由模型“答应不做危险操作”。对大型仓库，先建立入口/模块索引，用 `rg`、`git grep`、声明/调用关系检索定位最小相关文件；多阶段修改保持可复用的约束摘要，每个阶段提交最小 diff，跑编译和测试。在执行 Shell 时：最小权限、工作目录/路径限制、沙箱、工具白名单、高风险动作审批、dry-run 与备份回滚；关键词扫描仅作为辅助。

## 2026-10-20 中兴二面：TBench 飞书 Agent 的 ownership 边界 { #zte-20261020-agent }

来源：[中兴二面 · 问题 4](../../interviews/2026-10-20-中兴通讯-网络技术工程师二面.md#q4)、[问题 5：与网络岗位结合](../../interviews/2026-10-20-中兴通讯-网络技术工程师二面.md#q5)。`[learning] [interview] [project]`

### 我现场的理解与回答

我先说使用已有 Agent SDK，面试官追问“别人已经设计好的是吧”，然后解释大模型输出有不确定性，需要代码校验，进一步描述“飞书自然语言输入→后台服务→Agent 解析 TBench 参数→框架做参数检查→执行测试→辅助分析失败日志→飞书反馈”。

**现场已说到的正确边界**：Agent 不负责直接无条件执行；自然语言和测试参数之间应有确定性程序层，且本人集成工作与底层 Agent SDK 开发不同。

**现场没讲清的**：哪些消息回调/进程/执行接口由自己编码实现，参数 schema 具体是什么，错误检查覆盖什么范围，任务结果如何映射回用户。面试官问“是不是别人设计好的”，是在验证本人贡献，不是说调用 SDK 没价值。

**待核实的事实**：目前没有对应企业内部 TBench 源码和 commit 可以访问；不能将本知识页里更完善的权限校验、白名单、幂等、dry-run、审计自动认定为实际已做。上方“可控链路”是推荐设计，不是历史实装清单。

### 为什么对中兴网络技术工程师有价值

我在岗位匹配题中主要说重复动作与 AI 工具，但没有落到网络设备的**开通与配置检查、批量状态采集、故障日志和告警初筛、工单归档、客户验收**。迁移时应保留“模型负责理解和辅助分析、程序负责安全确定性执行”的分工，现场设备变更始终要遵循权限、审批与回退流程。
