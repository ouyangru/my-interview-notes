## Linux 驱动模型：面试中的最小完整框架

可以先把 Linux 驱动理解成三类对象的匹配：

1. **设备**描述“有什么硬件和资源”，例如寄存器地址、中断、时钟、GPIO、DMA 通道；嵌入式平台常由设备树提供。
2. **驱动**描述“怎样控制这一类硬件”，注册到相应总线或子系统，并提供匹配表与回调。
3. **总线 / 设备模型**负责匹配设备与驱动；匹配成功后调用 `probe`，移除或解绑时调用 `remove` 等清理路径。

`platform_driver` 只是常见例子。I²C、SPI、PCI、USB 等都有各自总线和匹配机制，不能把所有驱动都说成 platform 驱动。

### 一次常见开发流程

1. 读芯片手册和原理图，明确寄存器、时钟、复位、中断、总线和数据通路。
2. 确认硬件如何被描述：设备树节点、ACPI/PCI/USB 枚举或板级信息。
3. 选择正确内核子系统，而不是先随意创建字符设备。例如摄像头进入 V4L2/media，eMMC host 进入 MMC 子系统，网卡进入 netdev。
4. 注册驱动和匹配表；匹配成功进入 `probe`。
5. 在 `probe` 中获取并校验资源，初始化硬件，注册到上层子系统；每一步都要设计逆序清理。
6. 实现数据路径、中断/DMA、并发与电源管理；处理错误、超时、拔出或 suspend/resume。
7. 配置为内建或模块，结合设备树和内核配置构建。
8. 用内核日志、sysfs/debugfs、实际 I/O 和错误注入验证；出现问题时先判断是“没有匹配”“probe 失败”“接口注册失败”还是“运行时数据路径失败”。

### 推荐口述

> 我没有独立写过 Linux 驱动，所以不会把源码阅读说成驱动开发经验。我的理解是，Linux 驱动开发不只是操作寄存器，而是先确认硬件资源和所属子系统，再通过设备树或枚举信息描述设备，注册对应 bus/subsystem 的 driver 和匹配表。匹配成功后进入 probe，获取 MMIO、中断、时钟、GPIO、DMA 等资源，初始化硬件并向上层子系统注册接口；运行时再处理 I/O、中断、并发、错误和电源管理，退出时逆序释放。验证时要区分没有 match、probe 失败、接口注册失败和真实数据路径失败。我目前缺的是亲手完成和调试这一整条链路。

## eMMC 从应用 I/O 到控制器的分层链路

下面是面试可用的**概念链路**，不是某一内核版本的逐函数承诺：

```text
read/write 或文件系统请求
        ↓
VFS / 文件系统 / 页缓存
        ↓
通用块层组织 bio / request，调度并提交
        ↓
MMC block 层把块请求转换为 MMC 命令/数据请求
        ↓
MMC core 负责卡识别、协议状态与 host 交互
        ↓
具体 MMC host controller driver 配置寄存器、DMA/中断并发起传输
        ↓
eMMC 设备
        ↓
中断/完成回调逐层完成请求，向上返回状态
```

不同内核版本的块层和 MMC 实现细节会变化；面试前如要讲具体函数，必须基于自己真正读过的内核版本重新核对。不能只背 `bio`、`request_queue`、`mmc_request` 等名词后假装看过完整代码。

### 为什么“有排队”不够

排队只是通用块层的一部分。完整说明至少要交代：

- 请求从哪里进入，逻辑块地址和长度如何传下去；
- 通用块层与 MMC 子系统各负责什么；
- MMC core 与具体 host controller driver 的边界；
- DMA/中断或轮询怎样完成数据传输；
- 超时、CRC、卡状态等错误怎样向上返回。

### 推荐口述

> 我当时只记得读写请求会排队，说明源码阅读还没有形成完整链路。复盘后我会按层次理解：应用 read/write 经过 VFS、文件系统和页缓存形成块 I/O，通用块层把 bio 组织成 request 并提交；MMC block 层把块请求转成 MMC 请求，MMC core 处理协议和卡状态，再调用具体 host controller driver 配置寄存器、DMA 和中断，把命令发给 eMMC；完成后状态再逐层返回。这个是我现在整理出的通用框架，具体平台的函数名和我实际看过的范围还需要回源码核实。

## 类 Linux 教学 OS 与 Linux 的差异

不能回答成“只是 Linux 版本更早”。更稳妥的比较维度是：

| 维度 | 教学型类 Linux OS | 真实 Linux |
| --- | --- | --- |
| 目标 | 展示启动、内存、进程、文件系统等核心机制 | 支撑大量架构、硬件与生产场景 |
| 设备模型 | 常是少量静态设备和简单回调 | bus/device/driver、子系统、sysfs、设备树/枚举 |
| 驱动范围 | 教学设备或少量控制器 | 大量真实控制器、热插拔、DMA、PM、错误恢复 |
| 并发与可靠性 | 机制简化，场景受控 | SMP、抢占、锁、引用计数、生命周期和错误路径复杂 |
| 生态 | 自包含课程代码 | Kconfig、模块、稳定用户 ABI、工具链和社区维护 |

项目表达应该先交代上游框架、自己真正修改与验证的模块、没有做过的部分；不能因接口名类似 `open/read/write` 就把它等同于完整 Linux 驱动框架。
