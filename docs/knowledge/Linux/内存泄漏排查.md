## 我当时的回答

我当时主要从“如何避免内存泄漏”的角度回答，比如观察裸指针、注意 `malloc/free` 或 `new/delete` 是否释放、尽量用智能指针自动管理资源，并提到可以用 Linux 命令检查。

这个回答的问题是：它更像 C++ 资源管理常识，不像 Linux 线上/板端问题排查流程。面试官问的是“发现系统里有内存泄漏后怎么排查”，重点应该是确认现象、复现路径、定位分配栈和验证修复。

## 易错点

- `[weak]` 不要一上来就说“用智能指针”。智能指针是预防和代码设计手段，不是完整排查方法。
- `[weak]` 不能只说“Linux 命令”，要说具体观察什么指标，比如 RSS、VmRSS、heap、mmap、线程数、fd 数等。
- `[weak]` 嵌入式板端工具可能受限，需要准备“没有 ASan / valgrind 时怎么查”的降级方案。

## 推荐排查路径

1. 先确认现象：进程 RSS 是否持续增长，增长是否和某个请求、定时任务、连接、模块操作有关。
2. 查看进程级指标：`top`、`ps`、`pmap`、`/proc/<pid>/status`、`/proc/<pid>/smaps`。
3. 尝试稳定复现：构造固定操作路径或压测，让泄漏可重复出现。
4. 开发环境优先使用工具：ASan、valgrind、heap profile、tcmalloc/jemalloc profiling。
5. 板端工具受限时做降级定位：在可疑模块加分配/释放计数、生命周期日志、对象数量统计。
6. 重点检查代码：异常返回路径、错误分支、容器只增不减、timer/callback 未注销、socket/session 未释放、线程未退出、`shared_ptr` 循环引用。
7. 修复后验证：长时间压测，观察内存曲线是否稳定。

## 推荐口头回答

如果系统疑似内存泄漏，我会先确认现象，而不是直接改代码。第一步是观察进程内存是否持续增长，比如用 `top`、`ps`、`pmap`、`/proc/<pid>/status` 看 RSS、VmSize、VmRSS 的变化，并结合操作路径判断是不是某个请求、某个定时任务或某个连接创建后没有释放。

第二步是尽量构造稳定复现路径。如果开发环境可以复现，我会优先用 ASan、valgrind，或者 tcmalloc/jemalloc 的 heap profile 去定位未释放对象的分配栈。这样能直接看到是哪条调用链申请了内存但没有释放。

第三步是在嵌入式板端工具受限的情况下做降级排查，比如在可疑模块加申请/释放计数，给 session、timer、callback、socket、buffer 这类对象打生命周期日志，再通过压力测试观察哪个对象只增不减。

代码层面我会重点检查 `malloc/free`、`new/delete` 是否成对，异常返回路径是否漏释放，容器是否只增不减，回调注册或定时器是否没有注销，C++ 中还要注意 `shared_ptr` 循环引用。最后修复后要通过长时间压测确认内存曲线稳定。

## 2026-10-15 C++ 开发一面：长期慢性泄漏 { #cxx-20261015-slow-leak }

来源：[C++ 开发岗位一面 · 问题 5](../../interviews/2026-10-15-公司未确认-C++开发岗位一面.md#q5-leak)。这次再次只答到“用 `top -p` 看进程是否持续增长”，面对“一天几十兆、半个月或一个月后才 OOM”的追问明确说没有用过工具。它与 2026-07-01 小鹏一面是同一排查链路的第二次真实面试证据，因此维持 `[weak] [interview]`，标为重复薄弱点；看完下面的方法不升级状态。

### 慢泄漏为什么不能靠临时盯 `top`

一个月才出问题意味着信号很弱，必须把**时间、负载和对象数量**放到同一张证据链中：

1. 固定间隔采集 RSS/PSS、匿名映射、线程数、fd 数、连接数、队列长度和关键对象数量；
2. 同时记录请求量、设备事件、定时任务和版本，让内存斜率能与业务动作相关；
3. 区分真正不可达对象、仍可达但无界增长的容器/队列、allocator 缓存、mmap 和页缓存；
4. 在相同负载下比较 heap profile 快照，关注“持续增长的分配栈”，而不是只看某一次最大的分配；
5. 修复后使用相同或更长时间窗口验证斜率进入平台期。

### 工具只按能力边界表述

- 开发环境可尝试 ASan/LSan、Valgrind、jemalloc/tcmalloc profiling；它们分别有性能、内存和平台限制。
- 板端不能运行重型工具时，给 session、timer、callback、buffer、发送队列增加创建/销毁计数、高水位和分配来源日志。
- 当前只有方法学习证据，没有在真实项目中使用上述 heap profiler 的证据；面试时应说“我会这样查”，不能说“我用它定位过”。

### 90 秒推荐回答

> 对一天只涨几十兆的慢泄漏，我先做长期采样，确认增长的是进程 RSS/PSS 中哪类映射，并把斜率和请求量、连接数、定时任务、队列高水位对应起来，避免把页缓存、allocator 缓存或背压问题误判成泄漏。开发环境能复现时，我会用 LSan/Valgrind 或 allocator heap profile 定期抓快照，比较持续增长对象的分配栈。板端工具受限时，就给可疑对象加创建销毁计数和生命周期日志，逐模块缩小范围。最后用同样负载跑更长时间，确认内存曲线进入平台期。相关工具我目前是了解排查思路，没有实际线上使用经验。
