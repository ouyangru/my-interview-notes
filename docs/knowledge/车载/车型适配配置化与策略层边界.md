# 车型适配、配置化与策略层边界

## 状态

`[learning] [interview] [project]`

## 来源

- 2026-06-25 速腾聚创嵌入式软件一面
- 经纬恒润 TBox 实习中的远程控制、车况数据上报、设备监控等模块
- 当前简历：经纬恒润经历中写到 TBox Linux 应用软件开发与维护、远程控制、设备监测、语音通话及车况数据上报；小鹏经历中写到 TBox 状态报告查询、车型和终端维度数据处理。

## 我真实被问到的点

速腾聚创这场里，面试官追问了“不同车型适配时具体怎么改”。我当时举了车况数据上报的例子，说不同车型需要上报的数据、格式、标签、时间戳和类型可能不同；有些老车型不需要上报标签，新车型需要加标签，所以只能参考原有车型框架再修改代码。

这段回答的问题不是方向完全错，而是容易让人感觉“车型差异都靠改代码硬适配”。如果面试官继续追问配置化、策略层、可维护性，就必须能说清楚什么适合配置，什么必须进代码，什么要抽到策略层。

## 我的理解

车型适配本质上是在“公共能力”和“车型差异”之间划边界。公共能力应该沉到框架层，比如通信链路、报文发送、ACK 处理、超时重试、日志和错误码；车型差异则应该尽量收敛在配置或策略里，比如上报哪些信号、字段映射关系、阈值、周期、是否带标签、不同版本的协议字段。

配置化适合处理“数据驱动的差异”，也就是字段、开关、阈值、映射、周期这类变化。策略层适合处理“流程或规则有差异，但仍有统一接口”的情况，比如不同车型的车况上报策略、故障成熟条件、远控前置条件。直接改业务代码只适合处理“能力本身变化、协议结构变化很大、历史框架没有预留扩展点”的情况，但这类改动要特别注意回归测试和旧车型兼容。

## 推荐口头回答

我理解车型适配不能简单理解成每来一个车型就复制一份代码去改。更好的做法是先把共性的链路和差异点分开。比如 TBox 车况数据上报里，公共部分是采集状态、组织上报结构、走网络链路发给后台、处理 ACK 和异常；差异部分可能是不同车型要上报哪些字段、字段映射、上报周期、是否带标签、协议版本字段等。

如果差异只是字段、开关、阈值、映射关系，我更倾向于通过配置文件或数据库配置来处理，避免频繁改代码。如果不同车型的处理流程有差异，但仍然可以抽象成统一接口，就可以放到策略层，比如为不同车型选择不同的上报策略或解析策略。只有当协议结构变化比较大、原来框架没有预留扩展点，或者确实涉及新增业务能力时，才需要改代码。

我之前现场举的例子是车况数据上报。老车型可能不需要上报某些标签，新车型的软件需求里要求加标签、时间戳或类型字段，这时如果原框架没有配置化能力，就只能在原车型框架上改代码适配。但从复盘角度看，这类需求后续应该沉淀成更清晰的配置或策略边界，否则车型越多，维护成本和回归风险都会变高。

## 易错点

- `[learning]` 不要把车型适配讲成“照着老车型代码改一改”。要先说公共框架，再说差异点放在哪里。
- `[learning]` 配置化不是万能的。字段、阈值、开关、映射适合配置；复杂流程差异更适合策略层；底层能力变化通常还是要改代码。
- `[project]` 如果说“只能改代码”，要补一句“这是因为原框架没有预留配置化入口 / 历史车型需求差异较大”，否则会显得工程设计意识不足。
- `[interview]` 面试官追问车型适配时，重点通常不是某个字段，而是维护性、复用性、回归风险和扩展性。

## 项目连接

- 经纬恒润 TBox：远控、车况数据上报、设备监控都可能存在车型差异，适合用“公共链路 + 配置/策略差异”的方式回答。
- 小鹏健康系统：终端、车型、模块维度的数据过滤和查询优化，可以作为“车型维度数据如何组织”的补充连接，但不要把它和 TBox 量产车型适配混为一谈。
- 简历追问：如果面试官问“你做过车型适配吗”，回答重点应该是：我接触过不同车型需求导致的字段和协议差异，能理解配置化和代码适配的边界，但不要夸大成自己主导了完整平台化架构。
