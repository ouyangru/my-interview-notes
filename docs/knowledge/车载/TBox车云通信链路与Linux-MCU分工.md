## 我真实被问到的点

速腾聚创这场主要追问的是：TBox 是什么，它在车上起什么作用，手机 App、云后台、TBox Linux 侧、MCU、CAN 和其他 ECU 之间的链路怎么走。现场回答里我说出了“手机后台与车载其他 ECU 的中间节点”“远程打开空调”“云平台通过 MQTT 下发到 TBox”“Linux 侧解析后发给 MCU”“MCU 组织 CAN 报文发给其他 ECU”“响应再上报云端”这条主链路。

问题在于，当时我把很多内容讲成了业务过程，没有把 Linux 和 MCU 的职责边界先讲清楚，导致面试官需要继续追问 TBox 是否联网、是否一直在车上、板子架构是什么、Linux 和 MCU 之间怎么通信。

## 我的理解

TBox 更稳的表述是“车云通信终端 / 车内外通信网关”，它不是单纯的业务进程，也不是普通意义上只负责某个车身功能的 ECU。它处在云端网络协议和车内总线协议的边界上，一边和 App / 云平台交互，一边和车内 ECU 交互。

远控链路可以固定讲成：

> 手机 App → 云平台 → MQTT/TCP 长连接 → TBox Linux 侧 → SPI/UART 板内通信 → MCU → CAN/LIN → 目标 ECU → 响应回传 → Linux 侧 → 云平台 / App。

Linux 侧的关键词是复杂协议栈和业务逻辑，主要负责联网、MQTT/TCP 连接、登录鉴权、心跳保活、数据解析、远控命令分发、车况/MSD/故障数据上报、日志和异常处理。MCU 侧的关键词是低功耗、实时性和车内总线，主要负责休眠唤醒、CAN/LIN 报文收发、部分硬件状态采集、对车身 ECU 的控制和状态转发。

## 推荐口头回答

TBox 可以理解成车上的车云通信终端，它一边和云平台通信，一边和车内其他 ECU 通信，所以它在远控、车况上报、故障上报、紧急呼叫这类功能里起到网关和协议转换的作用。

以远程开空调为例，用户在手机 App 上下发命令后，命令会先到云平台，再通过 MQTT 或其他长连接通道下发到 TBox 的 Linux 侧。Linux 侧负责联网、协议解析、鉴权、业务校验和命令分发，然后通过 SPI 或 UART 等板内通信方式把解析后的控制请求发给 MCU。MCU 根据约定组织 CAN 报文，发给空调或车身相关 ECU。执行结果回来以后，MCU 把响应回传给 Linux 侧，Linux 侧再上报给云端，最终 App 能看到执行结果。

所以我理解 TBox 的核心不只是写一个应用逻辑，而是在“云端协议”和“车内总线协议”之间做桥接。Linux 侧更适合复杂网络协议和业务处理，MCU 侧更适合低功耗、实时控制、唤醒和 CAN/LIN 这类车身总线交互。

## 易错点

- `[learning]` 不要只说“TBox 是车载 ECU”。可以说它是车内控制器之一，但面试里更应该强调“车云通信终端 / 网关”。
- `[learning]` 不要把 Linux 和 MCU 都说成“处理命令”。Linux 侧处理云端协议和业务状态，MCU 侧处理实时控制、低功耗和车内总线。
- `[learning]` 不要把 SPI/UART 讲成无差别的“硬件线”。SPI 更适合同板内较高吞吐、主从式同步通信；UART 更简单、线少、调试方便，但吞吐和时序能力弱一些。实际选型还要服从平台已有设计。
- `[project]` 讲远控、车况、MSD 时都要回到这条链路，不要每次重新从业务百科讲起。

## 项目连接

- 经纬恒润 TBox 实习：远程控制、车况数据上报、语音通话、设备监控、TCP MSD 上报、日志和调用栈定位都能挂到这条主链路上。
- 小鹏 TBox 实习：TBench、飞书机器人、状态报告查询优化、通信中间件虽然不是同一家公司项目，但模拟面试时可以继续围绕“车载端通信链路、测试闭环、日志定位”这条主线来讲。
- 简历追问时，如果面试官问“你 TBox 这段到底做了什么”，先用这条链路定位置，再说自己主要在 Linux 应用侧做功能适配、协议解析、异常处理和问题定位。

## 下一次应该怎么追问

1. 为什么 TBox 要拆成 Linux 侧和 MCU 侧，而不是全部放在 Linux 上做？
2. MCU 除了转 CAN，还可能承担哪些低功耗、唤醒和安全相关职责？
3. SPI 和 UART 在 Linux-MCU 通信里怎么选？如果链路丢包或响应超时，你会怎么排查？
4. 如果云端命令已经下发，但目标 ECU 没执行成功，你会按哪些层逐步定位？
5. 远控命令为什么需要 ACK、超时、重试和幂等？
