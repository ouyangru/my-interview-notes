# TCP 客户端与异步回调

- 状态：`[weak] [wrong] [interview] [project]`
- 来源：2026-06-22 影石相机 UI 开发实习一面
- 项目连接：经纬恒润 T-Box MSD 上传接收侧；公司封装 TCP 接口；两层回调；ACK / 响应报文异步接收

## 我的理解

这次面试里最容易出错的点不是“有没有用过 socket”，而是把原生 socket API、公司封装接口、业务回调三层混在了一起。以后必须先把边界立住：底层机制是 Linux socket；公司框架封装连接管理、事件循环、断线重连、数据收发通知；我实际参与的是 MSD 上传链路的接收侧处理，重点是回调里解析 ACK 或响应报文，而不是自己手写完整建连框架。

更准确的两层回调理解是：第一层是连接状态回调，通知业务层 TCP 客户端是否连接成功、断开、异常或重连；第二层是数据接收回调，底层在 socket 可读时收取并解析完整业务报文，再异步通知业务层处理 ACK / 响应。第二层不能说成“等待接收数据”，因为“等待”容易被理解成业务线程阻塞在 `recv()` 上。

## 易错点

- `[wrong]` 不能说“客户端绑定远程服务端 IP 和端口”。常规客户端主流程是 `socket -> connect -> recv/send`，服务端才是 `socket -> bind -> listen -> accept -> recv/send`。
- `[wrong]` 不能说“connect 以后获取 fd”。fd 是 `socket()` 创建时返回的，`connect()` 是在这个 fd 上发起连接。
- `[wrong]` 不能说“listen 监听 fd 的数据”。`listen` 是服务端监听连接请求，真正取出连接的是 `accept`，数据读写是 `recv/send`。
- `[weak]` 公司封装接口不要乱讲源码细节。可以说“我的理解是 fd 注册到事件循环，可读/异常时触发回调”，不要发明函数名或实现细节。

## 面试推荐回答

如果被问“经纬恒润 socket 开发是不是用公司封装接口”，可以回答：

> 是的，当时业务层用的是经纬内部封装过的 TCP 通信接口，不是我在业务代码里直接手写完整原生 socket 流程。我的理解是底层仍然基于 Linux socket 和事件循环，比如创建 socket、主动连接云端、把 fd 注册到事件循环里，fd 可读或异常时由框架触发回调；但连接管理、断线重连、收发事件分发这些已经被框架封装掉了。业务侧主要接触报文收发接口和数据到达回调。我这边更准确地说是参与 MSD 上传链路里的接收侧处理，框架收到云端 ACK 或响应报文后回调到业务模块，我再根据消息类型、流水号或结果码做解析和状态更新。底层 fd 事件循环和发送侧不是我主要负责的部分。

如果被追问原生 socket 流程，可以补充：

> 原生 socket 要区分服务端和客户端。服务端一般是 `socket -> bind -> listen -> accept -> recv/send`，客户端一般是 `socket -> connect -> recv/send`。`listen` 不是读数据，而是让服务端 socket 进入监听状态；`accept` 才是取出已经建立好的连接；连接建立后双方才通过 `recv/send` 收发数据。
