### 问题 2 · 远控或语音链路断开后如何恢复

#### 1. 面试官原问题

**面试官：**

> 比如说你在做这种远程控制、语音通话的时候，可能因为一些网络原因或者是调用原因导致这种断开，这种有没有比如说断点重连，或者这种降级的一些措施做过吗？

#### 2. 我当时的回答（全文）

**我：**

> 是这样，就是一般……我举个小例子吧。比如说我的一个远程控制，我稍微简单地介绍一下它的链路。比如说我在手机 App 上点开一个打开空调的按钮，那么云端就会向 TBox 下发一个指令，然后 TBox 这边的 Linux 把这个指令翻译好以后，再向 MCU 发送对应的控制信息。然后它这边会等待 MCU 的响应，也就是这个 ACK 的信息，以及后续这个控制执行的结果。
>
> 所以在这个过程中，如果说，比如说 Linux 的命令没有正常发送到 MCU 的话，其实在 Linux 这一侧会有一个定时重传的策略。如果三次以后还没有接收到对应的响应，那么我就会判定这一段控制是失败的，然后会返回一个控制超时的码到云端，表示这样的控制超时。
>
> 还有就是关于我之前实现的 MSD 上传这一块，也是存在一些，比如说网络断开了，那么 TBox 这边发送一些数据的时候肯定会存在一些问题。比如说 `send` 函数会返回……然后在这个过程中也会存在多次重试的操作。如果多次重试以后还是一个异常状态，就会进行 TCP 的重连。

#### 4. 复盘判断

- 结论：基本正确
- 状态：`[learning]`
- 历史标签：`[interview] [project]`
- 影响程度：中

#### 5. 当时回答的问题在哪里

- **正确的部分：**远控讲出了“等待 ACK/结果—超时重试—超过次数—失败上报”，MSD 讲出了发送异常后的重试和重连。
- **遗漏的关键点：**TCP 重连后是否重新鉴权、业务数据是否重发、怎样避免非幂等命令重复执行。
- **表达/结构问题：**先花较长篇幅重述远控业务链路，并把 MCU 命令超时与 TCP 连接恢复混在同一段回答里。

#### 6. 推荐回答（完整版本）

> 有，但远控和 MSD 的恢复机制不一样。远控本质上是命令—响应流程，Linux 把控制命令发给 MCU 后等待 ACK 和执行结果，超时后按策略重试，超过最大次数就返回控制超时或失败状态给云端，避免无限重试。MSD 是 TCP 长连接，如果 `send/recv` 报错或者检测到连接断开，就进入重连流程；重新建连后还要重新完成登录鉴权，再恢复业务数据传输。对于可能重复执行的业务，还需要结合序列号、ACK 和幂等性判断决定是否重发。

### 问题 3 · MSD 登录鉴权流程

#### 1. 面试官原问题

**面试官：**

> 我看你这个 MSD 上报模块，那这中间登录鉴权的过程能给我讲一下吗？

#### 2. 我当时的回答（全文）

**我：**

> 是这样，我的 TBox 如果要连接到远程的一个……因为我这个 MSD 上传在我这一块主要实现的作用，就是需要把车辆发生事故后生成的一系列 MSD 信息发送到测试机构，然后测试机构检查这些数据是否符合国家标准。所以如果 TBox 要进行 MSD 上传，需要有一个登录鉴权的作用。
>
> 也就是说，在建立好 TCP 连接以后，首先会向测试机构发送账号和密码，这个账号密码是测试机构那边提供的。发送完账号密码之后，会接收到测试机构回传的响应，这个响应会存在一些内容，比如登录是否成功，或者还有一些异常状态。
>
> 如果接收到响应并解析以后发现登录成功，就会进行下一步操作；如果登录密码错误或者发生了超时，TBox 这边会返回一个错误。就是如果登录失败的话，会取消掉这一次 MSD 的……或者会重新进行登录。我记得当时会存在比如说 60 分钟的超时，如果 60 分钟以后登录还是失败，那么便会取消掉这一次 MSD 数据上传。接收到登录成功的响应以后，后续才会进行 MSD 业务数据发送。

#### 4. 复盘判断

- 结论：基本正确
- 状态：`[learning]`
- 历史标签：`[interview] [project]`
- 影响程度：中

#### 5. 当时回答的问题在哪里

- **正确的部分：**讲清了 `TCP 建连 → 登录请求 → 登录响应 → 成功后进入业务态` 的主状态机。
- **遗漏的关键点：**登录报文封装、响应码解析、重连后必须重新登录，以及登录失败和超时策略的边界。
- **表达/结构问题：**背景介绍偏长；“60 分钟”属于记忆不确定的具体数字，容易引出无法验证的追问。

#### 6. 推荐回答（完整版本）

> MSD 连接建立后不会直接上传业务数据，而是先进入登录状态。TBox 按协议封装登录请求并携带测试机构分配的鉴权信息，服务端返回登录 ACK，我们解析响应码，只有登录成功后状态机才进入业务态，后续才发送 MSD 数据和心跳。如果登录响应超时或鉴权失败，就按照协议策略重试，超过最大重试时间后终止本次上传；如果 TCP 中途断开，重连以后也必须重新完成登录，不能直接继续发送业务数据。

### 问题 6 · 所谓 Double Free 的具体场景

#### 1. 面试官原问题

**面试官：**

> 那讲一下你这个 Double Free 当时是什么样的一个场景呢？

#### 2. 我当时的回答（全文）

**我：**

> 是这样，当时在实现 MSD 上报模块的时候，我用的并不是 Socket 原生 API，它基本上在 Socket API 上又封装了一次。它这边的封装主要就是会创建一个 Handle 的……它会把 Socket 的文件描述符放入一个 Handle 当中。
>
> 这块确实我记得有点不太清，我只是依稀记得 Socket 会封装在一个 Handle 之中。然后在这个过程中，因为对整个封装逻辑可能不太熟，我先析构了它的 Handle，然后后续再把这个 Socket 进行 `close`。但是在析构 Handle 的过程中，本身就会把 Socket 文件描述符先关闭了，所以在这个过程中会出现两次关闭这样一个文件描述符的过程，也会导致进程出现异常。

#### 4. 复盘判断

- 结论：核心场景基本正确，但术语答错
- 状态：`[weak]`
- 历史标签：`[wrong] [interview] [project]`
- 影响程度：高

#### 5. 当时回答的问题在哪里

- **正确的部分：**已经讲清楚 RAII Handle 持有 fd、析构时自动关闭、外部再次手动关闭造成资源生命周期冲突。
- **错误的部分：**这不是 `Double Free`，而是 `double close`；`Double Free` 特指同一块动态内存被 `free/delete` 两次。
- **遗漏的关键点：**fd 数值可能被内核快速复用，第二次 `close` 不仅可能返回 `EBADF`，还可能误关后来复用同一整数值的新资源。

#### 6. 推荐回答（完整版本）

> 这里严格来说不是 Double Free，而是 double close。项目没有直接裸用 Socket，而是把 fd 封装在一个 Handle 对象中，Handle 拥有这个 fd，并在析构时自动调用 `close`。当时我没有弄清楚 ownership，在销毁 Handle 后又手动 `close(fd)` 一次，相当于同一个 fd 被关闭两次。后来把资源生命周期统一交给 Handle 管理，外部只使用而不再负责释放。fd 被关闭后整数值还可能被内核重新分配，如果第二次关闭发生得晚，极端情况下甚至可能误关一个新资源，所以资源所有权必须唯一且明确。

#### 8. 关联知识库

- [文件描述符与 Socket](../knowledge/操作系统/文件描述符与Socket.md) — `[weak] [wrong]`
- [移动语义与智能指针](../knowledge/C++/移动语义与智能指针.md) — 所有权与 RAII

- 我当时的回答：`[转写缺失]` 用户回忆为“有印象，但突然不知道怎么组织语言”。

#### 复盘判断

- 结论：不完整
- 状态：`[weak] [interview] [project]`
- 影响程度：高

#### 推荐口头回答

> epoll 默认是 LT，也就是水平触发，只要 fd 当前仍处于就绪状态，后续调用 `epoll_wait` 还会继续收到通知；ET 是边缘触发，主要在状态从未就绪变成就绪时通知，因此不会持续重复提醒。ET 模式下一般要把 fd 设成非阻塞，收到可读事件后循环 `recv` 直到返回 `EAGAIN/EWOULDBLOCK`，否则一次没有读完，剩余数据可能不会再次触发新的边缘通知。我的流媒体项目使用非阻塞 Socket 和 `EPOLLOUT`，核心是避免慢客户端阻塞事件循环；如果 `send` 只发送一部分，就记录偏移，如果返回 `EAGAIN`，等下一次可写事件再继续发送。

!!! note
    简历只写了 epoll、非阻塞 Socket 与 `EPOLLOUT`，没有写实际采用 ET；如果源码使用 LT，不要为了回答这道题声称项目使用了 ET。

#### 面试官原问题与我当时的回答

- 面试官问题：`[转写缺失]` 据回忆，询问 `shared_ptr` 是否线程安全。
- 我当时的回答：`[转写缺失]`。

#### 复盘判断

- 结论：无法根据原始材料判断现场具体答案；面试后仍需补课
- 状态：`[weak] [interview]`
- 影响程度：中

#### 推荐口头回答

> 要分三层看。多个不同的 `shared_ptr` 对象共享同一个控制块时，引用计数的增加和减少本身是线程安全的，所以不同线程各自持有副本通常没问题；但多个线程同时修改同一个 `shared_ptr` 对象，例如一个线程 `reset`、另一个线程赋值，并不天然安全，需要额外同步；同时，`shared_ptr` 的线程安全也不代表它指向的业务对象线程安全，多个线程同时修改 `*ptr` 仍然需要锁。也就是引用计数安全，不等于同一个智能指针对象的所有操作安全，更不等于被管理对象安全。

- 我当时的回答：`[转写缺失]`。

- 状态：`[learning] [interview]`
- 影响程度：中

#### 推荐口头回答

> 对于同一把读写锁保护的共享资源，读锁是共享的，所以读和读可以并发；写锁是独占的，只要线程持有写锁，其他读线程和写线程都不能进入，因此读和写不能同时进行，写和写也不能同时进行。它适合读多写少的场景，因为普通 mutex 会把读和读也串行化，而读写锁允许多个只读线程并发。
