**推荐口头回答：**

“这个项目不是从零开发一个板级 Linux 系统，而是在两个现成基础上扩展：一是全志 V853 开发板已有的 BSP、摄像头和媒体驱动，二是一个原先能处理静态网页请求的开源 HTTP Server。我负责的核心方向是将摄像头数据引入用户态服务，再组织为客户端能够消费的视频流，并且让一个摄像头视频源同时服务多个连接。

整条链路可以按四部分看。采集层从摄像头对应的接口获取数据；媒体层判断拿到的是 MJPEG/JPEG 还是 H.264，再按 HTTP-MJPEG 或 HTTP-FLV 等协议进行封装；会话管理层给每个客户端维护状态与队列；发送层通过 Socket 把数据持续发出去。与原本的静态 HTTP 请求不同，视频连接可能持续数分钟甚至更久，必须处理客户端消费速度不一致、发送不完整和缓冲区积压，所以我重点关注采集与发送解耦、每客户端独立排队、慢客户端丢旧数据这些问题。”

#### 6. 推荐回答（完整口头版本；不代表当时已说出）

**推荐口头回答：**

“Socket 可以把它理解成 Linux 给应用程序提供的网络通信入口。对于 TCP，我会先分服务端和客户端讲。服务端调用 `socket(AF_INET, SOCK_STREAM, 0)` 创建一个监听用的文件描述符，`bind()` 把它绑定到**本机**的 IP 地址和端口，`listen()` 让它进入被动监听状态；客户端调用 `socket()` 之后，用 `connect()` 指定**服务端** IP 和端口，发起 TCP 连接。连接建立后，服务端通过 `accept()` 返回一个新的已连接 FD，后续双方才在各自的连接 FD 上调用 `send()/recv()`，最后 `close()`。所以 `listen()` 和 `accept()` 不能混成一回事：前者使 Socket 可接受连接，后者取得一条已建立连接。”

“在我的 V853 视频服务器场景中，板端属于 TCP 服务端，浏览器/播放器一般是客户端。监听 FD 专门处理新连接，`accept()` 之后每个客户端都有一个独立连接 FD；用 epoll 可以让同一个事件循环管理多个客户端的可读/可写事件。新连接接收 HTTP 请求之后，要处理持续视频发送。由于 Socket 设置为非阻塞，一次 `send()` 可能只发送部分数据，也可能因为发送缓冲区暂时不可写而返回 `EAGAIN`，此时要保留当前媒体消息和 offset，等到可写时续发，而不是认为一调用 `send()` 就把一整帧发完。”

**原理展开：** `bind()` 绑定的是调用者的**本地**地址，不会把客户端 FD 绑定到服务器地址；客户端可以显式 bind 本地地址/端口，但普通场景通常由内核自动选择。监听 FD 和 `accept()` 返回的连接 FD 都是该进程 fdtable 中的整数索引，不是系统全局唯一的网络连接编号。`epoll` 只是通知用户态某个 FD 可能就绪，不替应用收发数据；`EPOLLOUT` 表示 Socket 写就绪，不等于“队列新到了一帧”。如果业务队列跨线程生产，还需单独的通知/同步设计，具体是否使用 eventfd 等必须回项目代码核实。
