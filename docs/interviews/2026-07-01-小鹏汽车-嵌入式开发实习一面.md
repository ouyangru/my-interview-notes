### 问题 4 · TCP 粘包 / 拆包怎么解决

#### 1. 面试官原问题

**面试官：**

> 有解决过 TCP 的粘包问题吗？或者你了解 TCP 的粘包问题要怎么解决吗？

#### 2. 我当时的回答（口语整理版）

**我：**

这边我有一点了解。TCP 粘包和拆包问题主要是因为 TCP 本身是流式传输协议，它不能保证每次传输的都是一个完整的包。操作系统在两个 IP 设备之间发送数据时，会更倾向于把 TCP 发送缓冲区填满以后再进行一次 TCP 数据发送。如果包过小，就会积累在发送缓冲区中，另一个 IP 接收以后体现为多个包在接收缓冲区里粘在一起，这就是粘包。拆包是因为包太大，相比发送缓冲区更大，所以接收端可能接收不到完整的 TCP 包。

要解决粘包和拆包问题，首先在应用层申请一个缓冲区。因为应用层协议会有魔数、版本号、消息头大小、消息体大小，所以在接收缓冲区中检测接收到的数据有没有满足消息头里定义的消息体大小要求。如果没有满足，就继续接收；如果满足，就按照完整消息解析。

#### 3. 复盘判断

- 结论：主干正确，但局部原因表述不够严谨。
- 状态：`[learning] [interview]`
- 历史标签：没有构成严重 `[wrong]`，但“发送缓冲区填满才发送”“包太大比发送缓冲区更大”这类说法需要修正。
- 影响程度：中

#### 4. 当时回答的问题在哪里

- 正确的部分：
  - 能说出 TCP 是字节流协议，不保留应用层消息边界。
  - 能说出应用层需要缓冲区和协议头长度字段。
- 不严谨的部分：
  - 原话：`会更倾向于把 TCP 发送缓冲区填满以后再进行一次 TCP 数据发送`。
  - 问题：TCP 何时发送受 Nagle、MSS、拥塞窗口、接收窗口、系统调度等因素影响，不能简单说“填满才发送”。
  - 原话：`包太大，相比发送缓冲区更大`。
  - 问题：应用层消息被拆开不是只因为比发送缓冲区大，TCP 分段、MSS、接收端 read 大小都可能导致一次 read 不完整。
- 遗漏的关键点：需要强调 `read()` 返回的是当前可读字节数，不等于一个应用层包；接收端要循环解析缓冲区。

#### 5. 推荐回答（完整版本）

**推荐口头回答：**

TCP 是面向字节流的协议，它只保证字节可靠、有序到达，但不保留应用层消息边界。所以发送端一次 send 的数据，在接收端可能被一次 read 读到一半，也可能多个应用层消息被一次 read 一起读出来，这就是我们常说的粘包和拆包。

解决方法一般是在应用层协议里自己做 framing。比如定义固定包头，包头中包含 magic、version、header_len、body_len、cmd、checksum 等字段。接收端维护一个应用层接收缓冲区，每次 read 到数据后先追加到缓冲区，然后循环解析：如果当前长度不够一个包头，就继续等；如果够包头，就解析 body_len，判断完整包是否已经到达；如果完整，就取出这一包处理，并把剩余字节留在缓冲区继续解析；如果 magic 不对，就做错误恢复或者断开连接。

这样无论底层 TCP 怎么分段、合并，应用层都能根据协议头恢复自己的消息边界。

- [TCP 粘包与应用层消息边界](../knowledge/网络/TCP粘包与应用层消息边界.md) — `[learning] [interview]`

### 问题 5 · 系统内存泄漏怎么排查

#### 1. 面试官原问题

**面试官：**

**我：**

关于内存泄漏，首先我觉得第一点是要着重观察代码里使用裸指针的情况。因为使用裸指针的话，如果没有及时把这些裸指针所指向的内容 free 掉，那么就很有可能出现泄漏。所以这里更倾向使用可以自动管理资源的智能指针，它能够自动构造析构。

其次是在开发者申请堆内存的时候，一定要注意有没有进行资源 free。第三点是可以使用 Linux 下的一些命令来检查有没有内存泄漏。不过我当时在实习过程中，可能是因为开发层次还不够，没有遇到过关于内存泄漏的问题。

- 结论：不完整，偏预防思路，缺少真实排查路径。
- 状态：`[weak] [interview]`
- 影响程度：高

#### 4. 当时回答的问题在哪里

- 正确的部分：能想到裸指针、堆内存释放、智能指针和 Linux 工具。
- 遗漏的关键点：没有说如何确认泄漏、如何观察 RSS/heap、如何复现、如何定位分配栈、如何在嵌入式工具受限时降级排查。
- 表达/结构问题：回答从“如何避免泄漏”开始，而不是从“发现泄漏后如何定位”开始。
- 如果我是面试官，为什么会继续追问：因为这道题考察的是 Linux 调试闭环，而不是 C++ 智能指针概念。

#### 5. 推荐回答（完整版本）

**推荐口头回答：**

如果系统疑似内存泄漏，我会先确认现象，而不是直接改代码。第一步是观察进程内存是否持续增长，比如用 top、ps、pmap、/proc/pid/status 看 RSS、VmSize、VmRSS 的变化，并结合操作路径判断是不是某个请求、某个定时任务或某个连接创建后没有释放。

第二步是尽量构造稳定复现路径。如果开发环境可以复现，我会优先用 ASan、valgrind，或者 tcmalloc/jemalloc 的 heap profile 去定位未释放对象的分配栈。这样能直接看到是哪条调用链申请了内存但没有释放。

第三步是在嵌入式板端工具受限的情况下做降级排查，比如在可疑模块加申请/释放计数，给 session、timer、callback、socket、buffer 这类对象打生命周期日志，再通过压力测试观察哪个对象只增不减。

代码层面我会重点检查 malloc/free、new/delete 是否成对，异常返回路径是否漏释放，容器是否只增不减，回调注册或定时器是否没有注销，C++ 中还要注意 shared_ptr 循环引用。最后修复后要通过长时间压测确认内存曲线稳定。

#### 1. 面试官原问题

**面试官：**

#### 2. 我当时的回答（口语整理版）

**我：**

实验室做的都是偏通信算法类工作，所以这两个项目都是我之前在学校期间自己开展的一些项目。第一个是偏视频软件，主要做数据采集和数据分发。第二个项目主要是对 Linux 内核和操作系统中一些操作系统方面的设计哲学进行学习。

我讲第一个视频采集与流媒体服务项目。它一开始是我想进一步把学到的一些 C++ 知识应用到小项目上的尝试。原本只是一个 C++ 服务器项目，也就是编写服务端，让手机访问一个网页，获取服务端网页数据。后来我觉得既然可以访问服务器端数据，那么服务端也可以不仅是电脑，也可以是 Linux 开发板。开发板可以搭载很多传感器，所以我觉得可以在这个服务器基础上实现多客户端访问板端采集到的视频数据。

总体流程是板端通过摄像头采集数据，然后这些数据在板子内部处理，转化为可以通过 HTTP 协议传输的格式，再分发给多个客户端。最终形式就是访问一个网页，网页里有实时视频。不知道这样您能理解吗？

#### 3. 复盘判断

- 结论：HR 面够用，但项目价值表达偏散；技术面不够。
- 状态：`[learning] [interview] [project]`
- 影响程度：中

#### 4. 当时回答的问题在哪里

- 正确的部分：能说明项目是自驱学习，不是实验室安排；能说明从 C++ 服务器扩展到嵌入式 Linux 板端。
- 遗漏的关键点：没有集中讲出 V4L2、mmap、epoll、线程池、多客户端、慢客户端队列/丢帧这些简历关键词。
- 表达风险：最后问“您能理解吗”会显得自己组织不稳。
- HR 视角：可以减少底层细节，但必须翻译成能力证明：嵌入式 Linux、网络服务、多客户端并发、板端调试。

#### 5. 推荐回答（完整版本）

**推荐口头回答：**

这两个项目不是实验室方向，是我为了补嵌入式 Linux 和系统软件能力自己做的。实验室更多偏通信和算法，但我求职方向更想往嵌入式 Linux、车载系统软件走，所以我自己做了视频采集分发项目和 x86 类 Linux 操作系统项目。

以 V853 视频项目为例，最开始我是想把一个普通 C++ 网络服务器迁移到嵌入式 Linux 开发板上，让多个客户端可以通过网页访问板端摄像头的实时画面。整体流程是摄像头通过 V4L2 采集视频帧，板端用 mmap 减少用户态和内核态之间的数据拷贝，然后服务端把采集到的视频数据封装成适合 HTTP 或流媒体传输的格式，再分发给多个客户端。

并发处理上，我用 epoll 管理多个客户端连接，用线程池处理连接注册、请求解析等任务。为了避免慢客户端拖慢采集线程，我把采集和发送解耦，给客户端维护发送队列，并设置队列上限；如果客户端长期消费不过来，就丢弃旧帧或者断开连接，优先保证实时性。最终效果是可以在网页上看到板端摄像头的实时画面，并支持多个客户端同时访问。

这个项目对我最大的价值，是让我把 C++ 网络编程、V4L2 采集、嵌入式 Linux 部署和多客户端并发处理串起来了。

## 本场整体表现

### 做得比较好的部分

- 有真实 TBox 经历，和小鹏岗位匹配度高。
- 设备监测 / DTC 未上报问题有真实定位链路，可以继续打磨成强项目故事。

- 对实习时间、地域、到岗稳定性回答比较明确，综合面最终通过。

### 最影响结果的问题

1. `[weak] [project] [interview]` 工程故事表达不稳定：面试官问“最难/最成功的问题”，现场容易先介绍功能或泛泛说“解 bug”，没有第一时间给出现象、定位、根因、方案、结果。
2. `[weak] [interview]` Linux 内存泄漏排查路径薄弱：回答偏“如何避免泄漏”，缺少真实排查流程和工具链。
3. `[learning] [interview]` TCP 粘包主干正确，但局部原因表述不严谨，需要稳定成“TCP 字节流 + 应用层 framing + 接收缓冲区循环解析”。

### 表达层面

- 是否经常没有先给结论：是，尤其项目题和最难问题题。
- 是否展开过多：是，容易先讲业务背景和功能介绍。
- 是否把“我不知道”之后的推理讲清楚：一般，内存泄漏题承认没有实践但没有补足推理路径。
- 项目题是否体现“问题 → 设计 → trade-off → 极端情况”：不稳定，V853 项目没有把慢客户端和采发解耦作为核心设计讲出来。

### 技术层面

- C/C++：能讲智能指针和基础开发，但还需要更贴近具体问题。
- Linux / OS：需要补 GDB、core dump、内存泄漏、进程异常定位。
- 网络：TCP 粘包、应用层协议、心跳、ACK、异常断连需要继续整理。
- 驱动 / 嵌入式：TBox 业务理解有基础，但要把 Linux–MCU、DTC、配置状态同步讲清楚。
- 项目设计：V853 项目需要按采集层、封装层、连接管理层、发送层组织。
- Coding：本场未涉及。
