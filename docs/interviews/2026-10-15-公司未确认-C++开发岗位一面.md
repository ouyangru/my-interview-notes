### 问题 3 · C++ 有哪些特点，如何理解封装、继承、多态 { #q3-cpp }

#### 1. 面试官原问题

> “因为岗位里是 C/C++，你讲一下你知道的 C++ 特点吧。”

#### 2. 我当时的回答（完整可读整理）

> 我个人理解，C++ 相比 C 最大的差别是面向对象，有比较重要的三个特性：继承、封装和多态。继承主要是为了减少重复代码，可以继承父对象来完成逻辑复用。多态是同一个对象在多态以后能做差异化动作。封装是提供比较抽象的接口，上层不用关注函数内部如何实现，只关注它的输出，比较利于分层设计。
>
> 我在经纬恒润实习时做过一个故障码上报的小模块。异常可能来自数据采集、数据上传云端或数据处理。它们有公共逻辑，例如定时检查硬件状态、多次检查，超时后认为模块故障并上报诊断错误码；但不同采集、上报、处理模块的错误码、定时器时间和次数又不一样。所以这里用到了继承和多态的思路：父对象包含定时检查和上报的公共逻辑，不同子类维护不同诊断错误码和差异化操作。这个模块让我对面向对象三大特性有了更深入的理解。

#### 3. 复盘判断

- 结论：不完整，项目例子有价值。
- 状态：`[weak] [interview] [project]`
- 影响程度：高。
- 正确部分：能说出封装、继承、多态，并能联系诊断模块的公共流程与差异化策略。
- 明确问题：把“C++ 相比 C 最大差别”几乎等同于面向对象，遗漏 RAII、模板/泛型、函数/运算符重载、异常、标准库、移动语义和多范式；“继承为了少写代码”过窄，继承首先应表达 is-a 与可替换性；“同一个对象进行多态”没有说明基类接口、虚函数和动态绑定。
- 表达问题：基础定义没有先说清，过早进入很长的项目故事。

#### 4. 推荐回答

> C++ 不是只比 C 多了面向对象，它是一门多范式语言。第一，它支持封装、继承和运行时多态，适合把稳定接口和不同实现分开；第二，它有模板和泛型编程，可以在编译期复用算法和容器；第三，它强调 RAII，把资源生命周期绑定到对象生命周期，文件、锁和内存都能自动释放；第四，现代 C++ 还有智能指针、移动语义、lambda 和标准库，用来更清楚地表达所有权和并发逻辑。
>
> 在我的诊断模块里，公共检查流程可以放在基类或组合对象中，不同故障类型实现各自的检查条件和错误码。如果确实需要通过统一接口调用不同实现，可以用虚函数形成运行时多态；如果只是复用公共能力，也要优先考虑组合，不能为了少写代码就滥用继承。

### 问题 4 · 智能指针、模板和泛型是否熟悉

#### 1. 面试官原问题

> “其他特性，比如智能指针、模板、泛型之类的，熟不熟？”

#### 2. 我当时的回答（全文整理）

> 我个人比较熟悉的还是偏 C++11，因为实习主要用 C++11 的知识。比如共享指针、〔转写推断：独占指针〕、lambda 表达式、`std::function`，还有 `auto` 关键字等。编程里智能指针用得会比较多一点，`auto` 可以自动匹配类型，进行类型推导。

#### 3. 复盘判断

- 结论：答偏且明显不完整。
- 状态：`[weak] [interview]`；智能指针为重复薄弱点。
- 影响程度：高。
- 失分点：问题明确问智能指针、模板、泛型，却只罗列 C++11 名词；没有解释 `unique_ptr/shared_ptr/weak_ptr` 的所有权差异、循环引用、控制块，也没有回答函数模板/类模板、编译期实例化和泛型约束。

#### 4. 推荐回答

> 智能指针方面，`unique_ptr` 表达独占所有权，不能拷贝但能移动；`shared_ptr` 通过控制块中的强引用计数共享所有权，最后一个强引用销毁时释放对象；`weak_ptr` 不增加强引用计数，常用于观察对象或打破循环引用。它们主要解决资源所有权表达和异常路径自动释放，不代表用了智能指针就一定没有泄漏。
>
> 模板是 C++ 泛型编程的基础。函数模板和类模板可以对类型或常量参数抽象，编译器在使用时实例化具体版本，例如 `vector<T>` 和通用算法。优点是类型安全、复用和通常没有运行时虚调用开销；代价是错误信息复杂、编译时间和代码膨胀，需要把接口约束写清楚。C++11 常用 `auto`、lambda、`std::function`、右值引用和移动语义，但这些名词要结合所有权和使用场景解释。

### 问题 5 · 内存泄漏与长期慢性泄漏如何定位 { #q5-leak }

#### 1. 面试官原问题与追问

> “现在有一个系统发生内存泄漏，有没有定位思路？”
>
> “如果接手别人写的代码，泄漏很少，一天只涨几十兆或几百兆，上线半个月、一个月后才被系统杀掉，这种怎么排查？有没有工具直接分析？”

#### 2. 我当时的回答（完整可读整理）

> 我觉得可以分两部分。第一部分是提前预防内存泄漏。持有一部分资源以后，使用完没有及时释放，会导致很多无用内存堆积，后续没有可用内存。所以程序员在用 `new` 或者〔转写识别为 `mlock`，结合语境无法确认原词〕申请内存以后，要及时释放。
>
> 后续排查会有一些对应指令，例如 `top -p` 可以查看某个进程的内存使用量，也可以定时查看进程内存有没有随时间持续增长。以上是我的理解。
>
> 像这种长期少量泄漏，我在实习过程中没有遇到过。我的理解是会有一些监控指令，像刚才提到的命令。我肯定存在一些工具，但是我用得不是很多。

#### 3. 复盘判断

- 结论：不完整；面对关键追问基本不会。
- 状态：`[weak] [interview]`，与 2026-07-01 小鹏一面的同题形成**重复薄弱点（至少 2 场）**。
- 影响程度：高。
- 正确部分：知道先观察进程内存曲线，也诚实说明没有实际使用过相关工具。
- 失分点：把“排查”回答成“预防”；只说 `top -p`，没有区分 RSS/PSS、heap、mmap、缓存、线程栈和队列积压；没有稳定复现、分配栈、快照差分、板端降级和修复后长稳验证；面试官追问一个月级别慢泄漏时，没有提出持续采样与 heap profiling。

#### 4. 推荐回答

> 我会先确认它真的是泄漏，而不是页缓存、mmap、线程增加、队列积压或 allocator 没把空闲页立即还给系统。先用 `top/ps` 和 `/proc/<pid>/status`、`smaps` 持续采样 RSS、PSS、匿名映射、线程数、fd 数，再把增长和请求量、连接数、定时任务或某种操作对应起来。
>
> 对一天只涨几十兆的慢泄漏，我不会只现场盯命令，而是建立小时或天级曲线，在相同业务负载下定期采集 heap profile 做快照差分。开发环境能复现时可以使用 ASan/LSan、Valgrind，或者 jemalloc/tcmalloc 的 profiling 去找持续增长对象的分配调用栈；这里我只了解方法，不能说自己实际用过。板端工具受限时，就给 session、timer、callback、发送队列、缓存等对象增加创建/销毁计数和高水位日志，逐模块缩小范围。修复以后再跑同等或更长时间的压力测试，确认曲线进入平台期，而不是只看进程暂时没崩。

### 问题 7 · 进程间通信方式与 GDBus { #q7-ipc }

#### 1. 面试官原问题与追问

> “讲一下进程间通信方式。”
>
> “GDBus 是企业自己封装的吗？”

#### 2. 我当时的回答（全文整理）

> 进程之间的通信有管道，分有名管道和无名管道；还有共享内存、Socket 通信以及 GDBus。
>
> 我在经纬恒润实习时，不同进程之间的控制消息一般通过 GDBus 互相发送。我认为它类似一种总线，会有一个进程管理不同进程之间的通信，类似 broker。一个进程想和其他进程通信，需要先把消息发送给 broker，再让 broker 处理。

#### 3. 复盘判断

- 结论：基础罗列不完整；GDBus 方向部分正确但概念模糊。
- 状态：`[weak] [interview] [project]`
- 影响程度：中。
- 正确部分：知道管道、共享内存、Socket；知道 D-Bus 常有总线守护进程负责路由。
- 失分点：遗漏消息队列、信号、信号量（同步）、Unix Domain Socket 等；没有按数据量、拷贝、同步、关系和跨主机能力比较；把 GDBus 本身说成 broker 不准确。GDBus 是 GLib/GIO 提供的 D-Bus API，D-Bus 才是消息总线协议/系统。

#### 4. 推荐回答

> Linux 常见 IPC 包括匿名/命名管道、消息队列、共享内存、信号、Unix Domain Socket，以及用于同步的信号量等。选型时我会看是否有亲缘关系、数据量、是否需要消息边界、是否跨主机、拷贝成本和同步复杂度。共享内存吞吐高，但同步和所有权要自己设计；Unix Domain Socket 接口统一、支持双向通信和权限控制，适合本机服务化进程。

### 问题 9 · TCP 与 UDP 的区别和使用场景

#### 1. 面试官原问题

> “TCP、UDP 了解得多不多？”

#### 2. 我当时的回答（全文整理）

> TCP 是面向连接的字节流传输协议，内部有流量控制、滑动窗口以及其他机制，保证客户端和服务端之间的可靠连接和数据有序传输。但是它没有消息边界，需要接收端对消息边界处理。它更适合需要可靠信息的场景。我在经纬恒润实习做 MSD 上传到测试机构时，用的是基于 TCP 的应用层协议，因为要保证数据集信息完整，便于测试机构做国标数据认证。
>
> UDP 是无连接协议，协议开销比 TCP 小，更适用于实时音视频和偏实时性的场景。

#### 3. 复盘判断

- 结论：基本正确，但深度不足。
- 状态：`[learning] [interview] [project]`
- 影响程度：中。
- 正确部分：连接/无连接、字节流/消息边界、可靠有序、滑动窗口、实时场景都说到了，并有 MSD 项目连接。
- 遗漏：TCP 不保证“应用消息完整”，应用层仍需 framing；还应提重传、拥塞控制、半关闭；UDP 保留数据报边界，但可能丢失、乱序、重复，实时不等于一定选 UDP。

#### 4. 推荐回答

> TCP 提供面向连接、可靠有序的字节流，有重传、流量控制和拥塞控制，但不保留应用层消息边界，所以 MSD 这类协议仍需要长度字段、序列号、校验和超时/ACK 逻辑。UDP 是无连接数据报协议，保留一报一报的边界，内核不替应用保证到达、顺序和去重，优点是控制开销小、没有 TCP 队头阻塞，适合应用愿意自己处理丢包和时延的场景。实时音视频可能用 RTP/UDP，也可能用 TCP 或 QUIC，最终取决于网络环境、时延和可靠性要求。

### 问题 16 · V4L2 mmap 缓冲区生命周期与数据覆盖

#### 1. 面试上下文中的问题

> 面试官继续听取同一项目困难；以下是用户主动给出的第二个问题。

#### 2. 我当时的回答（完整可读整理）

> 一开始基于 V4L2 和 mmap 完成摄像头数据采集，数据给到用户态时，我没有先把采集到的一帧完整复制到用户态缓冲区，就把驱动缓冲区交还给 V4L2 驱动，导致后续出现数据覆盖。
>
> 后来修改逻辑：把通过 V4L2 获得的一帧数据完整复制到用户态，再分发给不同客户端队列，之后才把缓冲区还给驱动。这样避免驱动缓冲区被覆盖影响最后网络发送。总体上，我在现有 HTTP 服务器上增加了 V4L2 采集、数据封装、客户端管理和网络发送链路。

#### 3. 复盘判断

- 结论：基本正确，而且当前源码能支持“QBUF 前完成拥有型拷贝”的主干。
- 状态：`[learning] [interview] [project]`
- 影响程度：中。
- 源码核实：当前 `v4l2_capture.cpp` 在 `VIDIOC_DQBUF` 后，从 mmap 地址构造 `vector` 或把 MJPEG chunk 插入 `mjpeg_frame`，调用 `publish_frame`，最后才 `VIDIOC_QBUF`。网络侧又构造拥有自身存储的 `shared_ptr<vector<unsigned char>>`。因此当前 ref 下，驱动 buffer 归还前已经完成必要拷贝。
- 边界：只能证明当前仓库 ref，不能仅凭当前代码断言录音所说的“最初错误版本”一定存在于某个历史提交；没有提交/日志证据时，它仍是现场陈述。
- 表达缺口：应明确 `DQBUF` 后应用暂时拥有 buffer，`QBUF` 后驱动可立即复用；`mmap` 只提供映射，不替应用延长 buffer 生命周期。

#### 4. 推荐回答

> `DQBUF` 后，这个 V4L2 buffer 暂时交给用户态处理；它的地址来自 mmap，但所有权仍受驱动队列协议约束。一旦 `QBUF`，驱动就可以立刻把同一 buffer 用于下一帧，所以网络线程不能长期持有这个 mmap 指针。我的处理是在 QBUF 前把有效字节复制到拥有自己存储的 `vector`，再用共享引用分发给各客户端；等最后一个发送引用释放，用户态副本才销毁。之后再把驱动 buffer QBUF，采集和网络生命周期就解耦了。

### 问题 17 · 何时接触 AI，如何评价 AI 编程 { #q17-ai }

#### 1. 面试官原问题

> “你什么时候开始接触 AI？在项目里怎么用？”

#### 2. 我当时的回答（完整可读整理）

> 如果说接触 AI，我觉得算比较早的一批，从 ChatGPT 3.5 和微软 Bing AI，大约 2023 年寒假就开始使用相关软件。平时无论做课题研究还是写代码，都会用 AI 协助，也会了解最新资讯。现在用得比较多的是 OpenAI 的 ChatGPT。实习中代码书写和文档生成也会使用 AI。
>
> 我认为 AI 已经是很强的代码生成助手，几分钟可以生成很多代码。开发者要关注提示词质量，需求是否描述得足够清晰完整。代码完成后要反复验证逻辑是否冗余、是否符合现有框架和代码习惯，测试也要比较完整，因为人工 review 不一定每一行都看得很好，所以比较依赖完整测试。

#### 3. 复盘判断

- 结论：基本正确，但“接触早”价值不大，工程闭环不够具体。
- 状态：`[learning] [interview]`
- 影响程度：低到中。
- 做得好的地方：明确 AI 输出需要 review、适配现有框架和测试验证，没有把生成等同于正确。
- 失分点：提示词被说成首要能力，缺少上下文、权限、数据保密、确定性校验、回滚和审计；“依赖完整测试”没有说明测试层级。

#### 4. 推荐回答

> 我从 2023 年开始使用生成式 AI，但我更关注如何把它放进可控工程流程，而不是接触时间。写代码时我会先提供真实接口、约束和验收条件，让 AI 生成小范围修改；随后自己审查 diff，运行静态检查、单测和必要的集成测试，涉及设备、权限或数据时不让模型直接执行高风险动作。文档和问题分析也保留原始日志与来源，避免模型把推测写成事实。AI 能提高探索和重复劳动效率，但需求澄清、架构取舍和最终责任仍在开发者。

### 问题 18 · Agent 与 Skill 的理解和实习应用

#### 1. 面试官原问题与追问

> 面试官追问 AI 在工作流程中的使用，并问 Skill “相当于什么、怎么写”。

#### 2. 我当时的回答（完整可读整理）

> 在工作提效方面，我用 AI/Skill 帮助自动生成一些重复信息，也把 AI 接入工作流程。小鹏实习时把自动化测试任务接入飞书机器人，接触到团队提供的 Agent SDK。它主要做自然语言解析，从自然语言或比较模糊的语言中推理参数或函数输入，这是普通 Python 脚本只做关键词匹配不容易做到的。后续需要对 Agent 推理出的参数做校验，判断是否符合要求，并做兜底策略。
>
> 实习期间也写过相关 Skill。我理解 Skill 是抽象某个模块的主要逻辑，减少重复向 AI 发送类似提示词。现在有工具可以创建 Skill，例如〔转写为 `cloud`，结合语境可能指 Claude，但无法确认〕有开源 Skill 和 Skill Creator，可以输入需求和模块代码规范，让它生成 Skill 并测试。我后续验收；生成的 Skill 不一定百分之百好用，需要反复调整和润色。

#### 3. 复盘判断

- 结论：有真实场景和风险意识，但概念表达松散。
- 状态：`[learning] [interview] [project]`
- 影响程度：中。
- 正确部分：Agent 做自然语言到结构化参数；输出需要 deterministic validation 和兜底；Skill 用于复用稳定流程与上下文。
- 失分点：没有讲清 Agent 的工具权限边界、白名单、幂等、审计和人工确认；把普通 Python 脚本描述成只能关键词匹配过于绝对；“Skill Creator 自动生成并测试”不能替代人工验收，也未说明 Skill 的具体构成。

#### 4. 推荐回答

> 在 TBench 飞书接入里，Agent 不直接执行任意命令，它只把自然语言解析成结构化任务参数。后面必须经过用户/群权限、设备和用例白名单、参数类型与范围校验、设备预检，必要时 dry-run 或人工确认，再调用确定性的 TBench 接口；执行过程记录任务 ID、日志和结果，重复消息要保证幂等，失败要可回滚或安全停止。
>
> Skill 可以理解为给模型复用的一组任务说明、领域规则、示例和必要脚本，把“这个任务应该按什么流程做、读哪些资料、如何验收”固定下来。自动生成只能产出初稿，仍要用正常样例、边界样例和失败样例验证。Python 完全可以做复杂规则和结构化校验；Agent 的价值是处理自然语言的不确定性，确定性执行与安全边界仍交给普通程序。
