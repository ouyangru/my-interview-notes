### 问题 2 · 无线通信研究到底研究什么，工程链路是否真实存在

#### 1. 面试官原问题

**面试官：**

> 你的专业是信息与通信工程，研究方向是无线通信。这个研究方向做了哪些研究？你说的边缘设备到底是什么？采集什么数据？边缘设备到边缘服务器通过什么技术传，是 Wi-Fi、蓝牙还是 4G/5G？

#### 2. 我当时的回答（全文）

**我：**

> 这个主要是在一个比较大的通感算一体化系统下，专门对通信层面做研究。我稍微介绍一下。整个系统相当于有两个节点，一个是边缘设备，还有一个边缘服务器。最终想实现对人体动作的识别，或者别的需要通过 AI 帮助识别的任务。
>
> 在边缘设备这一端主要做数据采集，这一块主要使用通感一体化的无线过程获得回波，然后对回波数据进行降维处理，再把降维后的数据通过无线网络上传到边缘服务器。边缘服务器接收到数据以后，把它送入 AI 模型推理，获得人体动作识别或其他 AI 任务的结果。
>
> 在这个过程中，我主要优化从边缘设备到边缘服务器的通信方式，比如哪个特征需要更多功率，或者给不同天线更大的功率，以保证最终任务的推理准确率。

#### 3. 现场继续追问与我的回答

**面试官追问 1：**

> 你说的边缘设备是采集信息的吗？主要是摄像头拍照片这些数据吗？

**我当时的回答 1：**

> 对，主要是用来采集信息。其实在我这个研究部分，不是用拍照获取传感数据，主要是通过发送一些雷达波，获得它的回波，然后再进行滤波以及降维处理。

**面试官追问 2：**

> 这个边缘设备不是你们做的吗？你们只是拿到数据以后分析和处理吗？

**我当时的回答 2：**

> 可以这么理解。它存在一个开源的数据集，不过我也可以自己生成这样的数据集，比如使用 MATLAB 程序模拟出可以获得的传感数据。

**面试官追问 3：**

> 那你的主要工作是在服务器做 AI 分析，还是中间的数据传输？中间通过什么方式传？Wi-Fi、蓝牙，还是别的？

**我当时的回答 3：**

> 主要是在从边缘设备到边缘服务器这一块，就是它的低维数据要怎么传输，看中间的数据传输。
>
> 这块显示是通过无线传输，利用无线信号在开放空间中的叠加特性……具体用什么传输的话，好像并没有涉及这一层。
>
> 就我目前开展的论文来说，其实并没有考虑到上一层是用 Wi-Fi 还是别的通信，更多主要做发射端的一些功率分配，以及接收端的波束赋形。至于使用什么技术的话……中间这个链路怎么传，在我了解的文献里更多就是用一个信道模型来建模，用一个 H 表示信道。

**面试官追问 4：**

> 你这个具体研究再细一点是什么？现在主要是在 MATLAB 里做，没有工程应用，对吗？

**我当时的回答 4：**

> 我本身考虑的是 OFDM 多载波信道传输，把对应特征调整到不同载波上，在这个过程中考虑波形对 PAPR 的影响。我这边主要是在保证 PAPR 的情况下制定通信策略，以保证之后推理的准确度。
>
> 确实，我这个研究方向可能更多还是停留在仿真层面，考虑的东西没有这么多。

#### 4. 复盘判断

- 结论：研究内容有真实主干，但工程边界说明太晚，前后口径易被理解为矛盾
- 状态：`[weak] [learning]`
- 历史标签：`[interview] [project]`
- 影响程度：高

#### 5. 当时回答的问题在哪里

- **正确的部分：**后续能明确说出 OFDM、多载波映射、功率分配、波束赋形、PAPR、任务推理准确率，也承认主要使用 MATLAB / 信道模型仿真。
- **问题原话：**一开始说“边缘设备采集 → 无线网络上传 → 边缘服务器推理”，听起来像已经搭建真实设备与无线链路；后来又说“不考虑 Wi-Fi 还是别的通信”“用 H 表示信道”。
- **遗漏的关键点：**没有在第一句话区分“系统概念模型”和“本人真实工程实现”；没有明确数据是开源数据集或 MATLAB 生成，而不是本人完成的雷达硬件采集系统。
- **表达/结构问题：**从抽象系统愿景讲起，导致对方连续做 ownership check。更好的顺序应是：研究性质 → 我的具体变量/目标 → 未覆盖的工程层。
- **为什么会被继续追问：**面试官来自真实蜂窝网络工程团队，对“无线传输”会自然追问具体 RAT、设备、协议栈和链路实现。

#### 6. 推荐回答（完整版本）

> 我的研究目前主要是通信系统建模和算法优化，不是已经搭建了一套 Wi-Fi 或 4G/5G 的工程链路。系统概念上是边缘端获得感知特征，再通过无线信道把特征传到边缘服务器做 AI 推理；但在我的实验里，感知数据主要来自公开数据集或 MATLAB 仿真，物理层链路也用信道矩阵建模，没有具体绑定某一种商用无线技术。
>
> 我具体做的是 OFDM 多载波场景下的特征映射和资源分配：根据不同特征对最终任务的重要程度，研究功率如何分配、不同载波和天线如何承载特征，同时考虑 PAPR 等物理层约束，优化接收端 AI 推理准确率。所以我的 ownership 是算法建模、仿真和优化，不是雷达硬件、Wi-Fi/5G 协议栈或真实边缘设备开发。

### 问题 4 · V853 项目中开源项目做了什么，你自己做了什么

#### 1. 面试官原问题

**面试官：**

> 第一个视频采集流媒体服务，是你自己买的开发板做的吗？HTTP 服务器是自己搭的吗？这个开源项目到底提供了什么？视频在哪里采，数据发到哪里？电脑是客户端还是服务器？

#### 2. 我当时的回答（全文）

**我：**

> 对，是我自己买的开发板。其实它一开始只是网上的一个开源小项目，本身是做 HTTP 服务器，只能够访问一些静态网页。我想着能不能在此基础上再加上视频流采集，然后能够通过网页看到实时的视频数据。
>
> 所以后续在原本 HTTP 服务器的基础上，又加了视频流采集、多客户端分发以及网络发送。

#### 3. 现场继续追问与我的回答

**面试官追问 1：**

> 这个 HTTP 服务器是开源项目，那最终服务器运行在哪里？是不是还提供了免费的服务器？

**我当时的回答 1：**

> 没有。这个服务器可以直接在嵌入式板子上运行，然后直接通过网络访问，因为嵌入式板子可以连 Wi-Fi。

**面试官追问 2：**

> 视频是板子采集，还是电脑采集？数据发送到哪里？电脑作为服务端吗？

**我当时的回答 2：**

> 是开发板上采集的数据，发送到我自己的电脑，电脑可以通过浏览器访问。
>
> 电脑作为客户端。开发板上采集的数据推送到电脑上，电脑可以通过网页查看开发板采集到的视频数据。

#### 4. 复盘判断

- 结论：基本正确，但系统角色和 ownership 需要更快说清楚
- 状态：`[learning]`
- 历史标签：`[interview] [project]`
- 影响程度：中

#### 5. 当时回答的问题在哪里

- **正确的部分：**主动承认 HTTP 服务器基于开源项目；说明自己的增量是视频采集、多客户端分发和网络发送；最终也说清板子是服务端、PC 浏览器是客户端。
- **表达问题：**前面用了“推到哪里”“推送到电脑”的说法，容易让人误解成电脑上另有服务端。没有在第一句话给出系统拓扑。
- **遗漏的关键点：**没有立刻区分开源基线、本人新增模块、现成硬件能力和未实现部分。
- **为什么会被继续追问：**面试官在确认简历 ownership，而不是单纯问 HTTP 概念。

#### 6. 推荐回答（完整版本）

> 整体拓扑先说清楚：V853 开发板既负责摄像头采集，也运行 HTTP / 流媒体服务端；电脑浏览器是客户端，通过局域网访问板子的 IP 和端口。
>
> 项目不是从零写 HTTP 服务器。开源基线只提供了 C++ HTTP 静态页面服务，我在这个基础上完成板端适配，并新增用户态视频采集、多客户端实时分发和持续网络发送。具体包括把 V4L2/mmap 采集接入服务端，设计 StreamManager 解耦采集和发送，为每个客户端维护独立队列，并用 epoll、非阻塞 Socket、EPOLLOUT 和发送 offset 处理持续流式发送。摄像头 Sensor、ISP 和硬件编码器底层不是我实现的，这些属于平台现成能力。

### 问题 5 · 手机点开视频后，完整网络数据路径是什么

#### 1. 面试官原问题

**面试官：**

> 比如你用手机看爱奇艺，从打开 App、点开一个视频开始，整个网络过程是什么样的？要经过哪些主要步骤，才能把视频显示出来？整个数据流的过程是什么？

#### 2. 我当时的回答（全文）

**我：**

> 我觉得我可能对 Android 这一块有一点不太了解。不过从打开一个……

**面试官打断：**

> 不用管 Android，跟 Android 没关系。所有平台、所有操作系统都是一样的。我只关注整个网络的中间过程，不关注是什么操作系统。

**我继续回答：**

> 如果在爱奇艺上打开一个视频，我的理解是先向爱奇艺维护的服务器发送一个获取视频数据的请求，然后爱奇艺服务器获取到这个请求以后，连续不断地向我的这个……[听不清]……推流。

#### 3. 现场继续追问与我的回答

**面试官：**

> 你这个只是说了应用层的表象，中间涉及哪些协议？在已经有网的前提下，访问一个网页或视频，第一步要做 DNS 解析，把域名解析成 IP；拿到 IP 后还要建立 TCP 连接，做三次握手。再往下有 TCP/IP 协议栈、IP 层、链路层和 MAC。完整的手机到服务器链路还要从应用经过手机 Modem，把数据调制成无线信号，发到基站，再到核心网、骨干网、公网和服务器。

**我当时的回应：**

> 对。这个找域名的过程需要讲什么……我可能……
>
> 我请教一下，这一部分是在计算机网络里面有讲述吗？确实这个链路还挺长、挺复杂。
>
> 这个知识点可能讲得不好，我没这么多印象。

#### 4. 复盘判断

- 结论：答错 / 基本不会
- 状态：`[weak]`
- 历史标签：`[wrong] [interview]`
- 影响程度：高

#### 5. 当时回答的问题在哪里

- **正确的部分：**知道客户端要向服务端请求，服务端持续返回视频数据。
- **错误/答偏：**第一反应是“Android 不太了解”，把跨平台的网络链路题误判成 Android 平台题。
- **遗漏的关键点：**DNS、TCP 三次握手、TLS/HTTP、IP 路由、链路/蜂窝接入、Modem、基站、核心网、公网/CDN、返回路径、客户端缓冲与解码。
- **表达问题：**没有先按层拆解；“发请求—服务器推流”只覆盖应用层现象，无法证明简历中的 TCP/HTTP/TBox/无线通信基础已经串成整体认知。
- **为什么影响很大：**面试官所在团队恰好负责 Android/TBox 到 Modem、基站、核心网、服务器的整条蜂窝网络通路，这题接近岗位核心基础。

#### 6. 推荐回答（完整版本）

> 我先假设手机已经完成 4G/5G 注册并建立了数据会话。用户点开视频后，应用先根据域名做 DNS 解析，拿到 CDN 或业务服务器的 IP；如果使用 HTTPS over TCP，就先向目标 IP 建立 TCP 连接，再完成 TLS 握手，然后发送 HTTP 请求。若业务使用 QUIC，则会走 UDP 上的 QUIC，但总体仍然需要域名解析和到目标 IP 的路由。
>
> 请求数据在主机协议栈里从应用层向下封装，经过传输层和 IP 层，再交给蜂窝数据接口。Modem 根据当前无线接入和承载配置，把数据处理成空口数据发送给基站；基站把流量送入运营商核心网，核心网再通过承载网和公网路由到 CDN 或服务器。服务器返回视频分片后沿反向路径回到手机，TCP/QUIC 负责可靠传输或拥塞控制，应用层做缓冲，播放器再完成解封装、解码和渲染。
>
> 如果继续深挖，我会把“手机已联网”前提再展开为 SIM 鉴权、注册、数据会话建立、IP 地址和 DNS 配置获取；但这部分我目前是原理理解，没有真实 Modem 协议栈开发经验。

> 我的课题解决的是“通信资源受限时，怎样优先传输对 AI 任务更有价值的特征”，属于任务导向通信的算法建模问题。它会考虑信道、功率、载波、PAPR 和最终推理准确率，但不会覆盖商用 Wi-Fi/5G 的入网、掉线恢复、协议栈和设备适配。所以它和真实蜂窝工程有理论关联，但不是同一种工作。
>
> 我求职转向 Linux/C++ 系统软件，是因为我希望把工程实现、调试和长期运行能力补起来。研究经历提供了通信理论、建模和优化视角；TBox 与 V853 经历则提供了协议、并发和设备端开发经验。两者可以互补，但我不会把算法仿真包装成真实 5G 工程经验。

### 问题 11 · 反问：团队到底负责哪一段链路

#### 1. 我的问题

**我：**

> 刚才我的了解，您这边主要做的是 TBox Modem 这一块开发吗？

#### 2. 面试官回答（按转写整理）

**面试官：**

> 不只是 Modem，整个链路都有。无论是 Android 上网到 Modem、到基站，还是 TBox 直接上网到 Modem，所有网络打通涉及的我们都做。目的是把 TBox 或 Android 系统到基站、再到服务器的 4G/5G 通道打通。除了 Modem，还包括 Modem 协议栈之上的中间件和网络服务。

#### 3. 复盘提取

- 这段确认了本场实际岗位更接近车载蜂窝网络 / Connectivity / Modem 上层软件，而不是最初投递的模型部署。
- 本场技术追问形成闭环：完整网络路径和 Modem 经验不是随机八股，而是团队核心工作。
- 后续若面这类岗位，应优先准备：蜂窝入网与数据会话、Linux 网络接口与路由、Modem 控制接口、网络状态机、掉网重连、DNS/TCP/TLS/HTTP 端到端链路。

## 本场整体表现

### 做得比较好的部分

- 对岗位流转、研究仿真边界和 Modem 未参与部分基本保持诚实，没有强行冒充真实 5G 工程经验。
- V853 项目能够说清开源基线、本人的视频采集/多客户端增量，以及“板端服务端、PC 浏览器客户端”的最终拓扑。
- MSD 能说出 SOS/eCall 场景、GPS/乘员等内容，也能说出外层 TCP 应用报文的 header/body/CRC、登录、心跳和响应解析。
- voice core 反复重启案例有真实现象、调用栈、版本差异和临时恢复措施，是比只讲“加日志、抓包”更有说服力的工程故事。

### 最影响结果的问题

1. **完整网络数据路径不会。** 在简历包含 Socket/TCP/HTTP/TBox、专业又是通信的背景下，没有主动说出 DNS → TCP/TLS/HTTP → IP → Modem → 基站 → 核心网 → 公网/CDN/服务器，是本场最直接的技术失分。
2. **研究和项目 ownership 边界总是到追问后才出现。** 一开始把抽象研究模型讲成“边缘设备真实采集并无线传输”，V853 也没有第一句话先画清服务端/客户端拓扑，导致面试官持续核验真实性。
3. **Modem / 蜂窝网络工程经验薄弱。** 不知道模组采购以后主机侧还要做哪些网络服务和状态管理，而这正是面试团队核心方向。

### 表达层面

- 是否经常没有先给结论：是。研究、V853、网络路径都先从背景或模糊理解讲起。
- 是否展开过多：研究系统愿景展开较多，但最关键的“只做 MATLAB/信道建模”出现很晚。
- 是否把“我不知道”之后的推理讲清楚：Modem 题承认不知道是对的，但后面又加入未经确认的板卡推测。
- 项目题是否体现 ownership：V853 和 MSD 最终能够说清，但需要改成“开源/现成部分 → 我做的部分 → 没做的部分”的固定顺序。

### 技术层面

- C/C++：本场没有重点考察。
- Linux / OS：主要通过 V853 服务端和 TBench 间接考察，没有深入 OS 原理。
- 网络：端到端路径明显薄弱；应用层协议封装有项目经验，但没有把 DNS、TCP/IP 与蜂窝承载串起来。
- 驱动 / 嵌入式：没有直接考驱动；对 Modem、模组集成和蜂窝网络服务缺少实际经验。
- 项目设计：V853 ownership 基本成立；研究课题和工程实现边界需要前置；MSD 两层协议边界需要稳定。
- Coding：本场未考察。
