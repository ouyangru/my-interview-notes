## 2. C 语言函数传参是值传递还是引用传递？

### 面试官原问题

“C 语言函数传参是值传递还是引用传递？”

### 我当时的回答

> “我觉得在最快的话是得看这个函数的声明方式吧。就如果我……在函数的声明的过程中……用那个引用的符号来修饰……那么我在调用的时候肯定传的就是我的一个引用的数据。但如果……不是引用数据的话，那么……会拷贝一份……”

### 现场继续追问与我的回答

面试官随后用指针参数继续追问：如果函数参数是一个 `int *`，在函数里把它置为 `NULL`，外面的指针会不会变化；如果希望外面的指针变化怎么办。

我的回答核心是：函数内部 `p = NULL` 不会修改调用者的指针本身；如果希望修改外部指针，可以传双重指针，然后修改二级指针所指向的那个指针。

### 复盘判断

**第一问答错，但后两问基本答对。** `[weak] [wrong] [interview]`

### 当时回答的问题在哪里

第一问把 **C 语言** 听成了 C++ 的语境，直接把 C++ 引用 `&` 带进来了。实际上 C 语言函数参数都是值传递，即使传入的是指针，本质上也是把“地址值”复制一份给形参。值得注意的是，后续对 `int *` 和 `int **` 的行为判断是正确的，说明底层理解并非完全不会，而是语言概念标签混淆。

### 推荐回答

“C 语言只有值传递。普通变量传进去的是变量值的副本，指针参数传进去的是地址值的副本，所以函数里把形参指针 `p` 改成 `NULL` 不会改变调用者的指针；如果希望修改调用者的指针变量本身，需要传二级指针 `int **p`，然后修改 `*p`。”

### 当时回答 vs 推荐回答

当时回答先进入 C++ 引用语境，给面试官造成“C/C++ 基础概念不稳”的印象；推荐回答直接用“C 只有值传递”定性，再用一级指针和二级指针解释现象，最短也最稳。

## 3. 局部变量、static 局部变量和大数组分别放在哪里？

### 面试官原问题

局部变量一般放在哪里？如果有 `static` 修饰呢？如果函数里定义一个很大的数组会发生什么？

### 我当时的回答

> “一般局部变量是在我的一个函数调用的时候会出现的一些变量……如果有这个 static 的一个修饰的话……会放在进程……数据段里面，然后如果没有 static 修饰的话，那么是会放在……栈里面，会随着我这个函数的调用结束而销毁。”

继续问大数组时，我回答它仍然会放在栈里、随着函数调用结束销毁，并补充了如果通过 `new` 创建对象则会在堆上，需要自己管理生命周期。

### 复盘判断

**前半部分基本正确，大数组问题不完整。** `[weak] [interview]`

### 当时回答的问题在哪里

面试官问“大数组会发生什么”，真正想考的通常不是生命周期，而是 **线程栈大小有限，大数组可能导致栈溢出**。当时只回答“它还在栈上”，没有命中风险点。

### 推荐回答

“普通非 static 局部变量通常位于当前线程栈上，函数返回后生命周期结束；static 局部变量具有静态存储期，通常位于数据段或 BSS。函数里如果定义特别大的局部数组，它同样通常占用线程栈，而线程栈大小有限，所以数组过大可能造成 stack overflow。需要大块动态内存时一般考虑堆分配或其他更合适的存储方式。”

## 4. 结构体为什么会有内存对齐？`char + int` 的 `sizeof` 是多少？

### 面试官原问题

结构体里有一个 `char` 和一个 `int`，`sizeof` 大概是多少？为什么？有没有办法改变对齐？

### 我当时的回答

> “首先这个 char 是一个字节，int 是四个字节……结构体会存在一个内存的……为了保证 CPU 的访问能够更加快速……应该是……我记得有一个 pragma……加上这个东西的话……会取消掉结构体的……这样子可以优化一下内存。”

### 复盘判断

**核心方向正确，但表达不稳定，且把压缩对齐说成‘优化内存’过于绝对。** `[learning] [interview]`

### 推荐回答

“假设 `int` 按 4 字节对齐，那么 `char` 占 1 字节以后通常会补 3 字节 padding，再存放 4 字节的 `int`，因此结构体大小通常是 8 字节。内存对齐是为了让 CPU 以更自然的边界访问数据；可以通过 `#pragma pack` 等方式改变对齐规则，但减少 padding 不等于无条件优化，因为非对齐访问可能降低性能，在某些架构上还可能受到硬件限制。”

## 5. TCP 为什么三次握手？为什么不是两次或四次？四次挥手又为什么是四次？

### 面试官原问题

TCP 三次握手怎么理解？为什么不是两次或者四次？四次挥手为什么通常需要四次？

### 我当时的回答

握手部分，我描述了客户端先发起请求，服务端回复 ACK 的同时发送自己的 SYN，客户端再回复 ACK；并用“本来请求和响应可以看成四步，但服务端 ACK 和 SYN 可以合并”来解释为什么是三次。

关于两次握手，我回答如果缺少客户端最后一次 ACK，服务端无法确认客户端有没有收到自己的握手请求。

关于四次挥手，我回答客户端发出断开请求后，服务端可能还有剩余数据需要发送，因此 ACK 和服务端自己的 FIN 不一定能够同时发送，所以通常形成四次。

### 复盘判断

**大方向正确，握手解释略绕，但核心没有明显错误。** `[learning] [interview]`

### 当时回答的问题在哪里

“因为四次可以合并成三次”可以作为辅助解释，但最核心的逻辑应该先说清楚：双方需要确认彼此收发链路正常并同步初始序列号；只有两次时，服务端无法确认客户端是否收到了服务端的 SYN。

### 推荐回答

“TCP 三次握手的核心是双方都要确认自己的发送和接收能力正常，同时同步双方的初始序列号。客户端先发送 SYN，服务端收到后通过 SYN+ACK 表示‘你的 SYN 我收到了，同时这是我的 SYN’，客户端再回 ACK，服务端这时才能确认自己的 SYN 也被客户端收到。两次不够，因为服务端无法确认客户端是否收到自己的 SYN；四次虽然逻辑上可以，但服务端对客户端 SYN 的 ACK 和自己的 SYN 可以合并。挥手时 ACK 和 FIN 往往不能直接合并，因为收到对方 FIN 只表示对方不再发送数据，而本端可能还有未发送完的数据，因此通常需要先 ACK，等本端数据发送完后再单独 FIN。”

## 6. CAN ID 是什么？为什么 ID 小的优先级高？

### 面试官原问题

CAN ID 起什么作用？多个节点同时发送时怎么仲裁？

### 我当时的回答

> “这个 CAN ID 主要是起到区分不同的一个节点作用嘛……如果两个节点同时向总线发送信号……如果我的 CAN ID 号更小……会有一个更高的优先级……另外一个节点看到总线上有比它 ID 更小的……就会等待下一次发送。”

### 复盘判断

**仲裁方向基本正确，但把 CAN ID 定义成‘区分节点’不准确。** `[weak] [interview]`

### 当时回答的问题在哪里

CAN ID 更主要是 **标识报文/消息类型并参与优先级仲裁**，不是简单的节点地址。接收端可以根据 ID 判断是否关注这条报文；总线仲裁使用逐位无破坏仲裁，显性位覆盖隐性位，因此在相同格式条件下数值更小的 ID 通常拥有更高优先级。

### 推荐回答

“CAN ID 主要用于标识一类报文，同时决定报文的仲裁优先级，并不是简单表示发送节点是谁。多个节点同时发送时会逐位仲裁，显性位会覆盖隐性位，因此某个节点一旦发现自己发送的是隐性位、总线上却读到显性位，就知道自己仲裁失败，会停止本次发送；所以在其他条件一致时数值更小的 ID 通常优先级更高。”

## 7. I²C、UART、SPI 的差异是什么？I²C 起始/停止条件是什么？为什么恒润用 SPI、小鹏用 UART？

### 面试官原问题

这一组问题围绕常见硬件通信接口展开，包括 I²C/UART/SPI 的线路和特点、I²C 起始/停止条件，以及为什么你两段 TBox 实习里 Linux 与 MCU 之间使用的通信方式不同。

### 我当时的回答

对 I²C，我记得只有两条线，一条时钟、一条数据线，也知道可以挂多个设备，但对具体机制没有稳定说出来；对 UART，我提到点对点、协议比较简单，但现场对线路数量和适用场景的描述比较混乱。面试官继续追问 I²C 的起始和结束信号时，我明确表示不知道。

随后我补充实际经历：经纬恒润的 Linux 和 MCU 之间使用 SPI，小鹏这边接触的平台使用 UART；我也曾经问过同事为什么不同公司方案不一样，得到的解释包括历史平台方案、数据交换频率和业务需求差异。我推测恒润侧 Linux/MCU 交换更频繁，因此使用 SPI；小鹏很多 ECU 间通信更多走以太网，Linux/MCU 间可能主要承载控制类命令，因此 UART 已经够用。

### 复盘判断

**这是本场最明显的基础薄弱区之一。** `[weak] [interview]`

### 当时回答的问题在哪里

问题并不是“完全没有项目经验”，而是接口基础没有形成稳定框架，导致现场只能靠零散记忆和项目猜测来组织答案。尤其 I²C START/STOP 属于典型基础题，直接不会会明显影响嵌入式岗位评价。另外，解释“为什么项目选 SPI/UART”时需要区分**确定事实**和**个人推测**，历史方案、硬件资源、吞吐、实时性、协议复杂度、调试成本都可能影响选型，不能只用“数据量大小”一个因素解释。

### 推荐回答

“UART 是异步点对点通信，典型使用 TX/RX，不单独传输时钟，双方通过波特率约定时序；I²C 使用 SDA 和 SCL 两根线，支持地址寻址，可以一条总线挂多个从设备；SPI 通常使用 SCLK、MOSI、MISO、CS，属于同步通信，典型情况下全双工、吞吐较高，但占用的信号线更多。I²C 的 START 条件是在 SCL 为高时 SDA 从高变低，STOP 是 SCL 为高时 SDA 从低变高。至于 TBox Linux 与 MCU 为什么一个平台用 SPI、另一个平台用 UART，我不会只从吞吐量判断，实际还要看数据量、实时性、硬件资源、拓扑、协议复杂度以及历史平台方案；我接触到的事实是恒润平台使用 SPI，小鹏部分平台使用 UART。”

## 8. 为什么 Bootloader / 启动流程要分阶段？

### 面试官原问题

为什么启动程序经常要拆成不同阶段，而不是一次性完成？

### 我当时的回答

我从 x86 教学 OS 的启动流程出发，回答 BIOS 完成硬件检查后，会加载启动盘第一个扇区到内存，而第一扇区只有 512 字节，不够完成整个系统启动，因此第一阶段只做有限初始化并加载第二阶段，再跳转执行；随后又联系到实际 SoC 启动中也常见第一阶段 Loader / 第二阶段 Loader 的设计，后者再负责加载内核、文件系统等更复杂任务。

### 复盘判断

**大方向正确，并且成功把项目经验连接到了真实 SoC。** `[learning] [interview] [project]`

### 推荐回答

“启动早期的执行环境非常受限，比如可执行空间小、DDR 可能还没有初始化、启动介质访问能力有限，所以第一阶段通常只做最小硬件初始化和后续镜像加载；等内存和更多硬件条件具备以后，再进入更完整的第二阶段 Bootloader，完成 DDR/设备初始化、镜像校验、内核加载和启动参数准备等工作。x86 传统启动扇区 512B 是这个思想的一个典型例子，嵌入式 SoC 的多级 Boot 也是类似逻辑。”

## 9. 已经有时间片了，为什么还需要优先级？FreeRTOS 怎么调度？

### 面试官原问题

如果进程/任务已经按时间片运行，为什么还需要优先级？FreeRTOS 了解吗？

### 我当时的回答

我回答不同任务会有不同紧急程度，因此需要让高优先级任务优先运行；但是对具体调度机制表述比较模糊。继续问 FreeRTOS 时，我直接表示实时操作系统这块不是特别了解。

### 复盘判断

**调度概念只答到直觉层，FreeRTOS 基础缺失。** `[weak] [interview]`

### 推荐回答

“时间片主要解决同一优先级任务之间如何公平分享 CPU，而优先级解决不同任务的重要性和时效性。以典型抢占式 RTOS 为例，只要更高优先级任务进入 Ready 状态，就可以抢占当前低优先级任务；同优先级任务之间再通过时间片轮转。FreeRTOS 至少需要掌握 task、priority、preemption、queue、semaphore、mutex，以及 ISR 和 task 之间如何安全通信。”

## 10. V853：慢客户端为什么要丢帧？如果一直丢怎么办？

### 面试官原问题

你的流媒体服务如何处理慢客户端？为什么要丢帧？如果网络一直很差、一直丢怎么办？

### 我当时的回答

我先解释采集线程持续产生视频数据，不同客户端发送速度不同，因此每个客户端维护自己的队列，队列里保存指向视频数据的引用/指针，慢客户端的数据会在自己的队列里停留更久；如果希望减小观看延迟，就限制队列长度，队列满后丢弃旧帧，不断补入新帧，从而保证看到的是相对实时的数据，而不是为了完整性让延迟越来越大。

我还明确说明做过实验：网络不好时丢帧会造成卡顿，尤其极端网络条件下更明显，但项目目标更偏实时预览，因此宁愿出现一定卡顿，也不希望积累很大的观看延迟。

面试官继续追问“如果一直丢怎么办”，我现场卡住了，意识到当前实现没有进一步考虑这种长期拥塞情况，只能回答如果网络已经差到无法稳定通过 TCP 发送，确实会持续丢帧，当时没有理清下一层策略。

### 复盘判断

**前半段是本场最有价值的项目回答之一，极端情况追问没有接住。** `[learning] [interview] [project]`

### 当时回答的问题在哪里

前面的设计动机和实时性 trade-off 是对的，真正缺的是“生产速率长期大于消费速率时，系统不可能靠有限缓存解决”这一层。需要主动认识到这是一个不可持续状态，然后给出降级策略。

### 推荐回答

“我这里首先要解决的是慢客户端不能反向阻塞媒体采集和其他正常客户端，所以把媒体生产和网络发送做了解耦，每个客户端维护独立发送队列，socket 可写时再通过 epoll 驱动继续发送。队列不能无限增长，否则内存占用和观看延迟都会越来越大，因此实时预览场景下我会限制队列长度，满了就优先丢旧数据，用完整性换低延迟。如果客户端长期发送速率都低于视频生产速率，那说明问题已经不能靠缓存解决，需要进一步做降帧率、降低码率，或者对长期严重拥塞的客户端直接断开。MJPEG 的帧相对独立，丢帧比较直接；H.264 存在参考帧依赖，严重积压时不能简单随机丢帧，更合理的是等新的 IDR / 关键帧重新同步。”

### 当时回答 vs 推荐回答

当时已经说清楚“为什么要丢旧帧”，这是正确的工程权衡；推荐回答只是在它上面再补一层：**长期拥塞时必须降级，而不是无限缓存或无限丢同一种数据。**

### 面试回答方法

这类项目题适合按“问题 → 设计 → trade-off → 极端情况”展开，比只背实现细节更能体现系统设计思维。

## 11. TBox 中 MCU 和 Linux SoC 分别负责什么？

### 面试官原问题

TBox 里为什么既有 MCU 又有 Linux SoC？两边分别负责什么？

### 我当时的回答

我把 MCU 的职责总结为三类：CAN 数据采集与发送、控制小型外设（例如 LED / 扬声器等）、在整机休眠时保持低功耗运行并负责必要条件下唤醒 Linux SoC。Linux 侧则负责更复杂的业务，包括通过 4G/5G 连接云端、协议解析、业务逻辑、数据存储，并通过与 MCU 的通信协议把云端控制命令进一步传递给 MCU 或其他 ECU。

我还结合恒润项目提到 Linux 与 MCU 的 SPI 通信协议里会通过类似 service ID / event ID 的字段区分数据语义。

### 复盘判断

**内容其实比较完整，主要问题是现场讲得太散。** `[learning] [interview] [project]`

### 推荐回答

“MCU 更适合承担实时性、低功耗和硬件控制相关任务，比如 CAN 数据采集、部分外设控制，以及 Linux SoC 休眠期间继续保持运行并负责唤醒；Linux SoC 的算力和系统资源更丰富，主要承担 4G/5G 联网、云端协议、复杂业务逻辑和数据存储。两者之间再通过 SPI/UART 等接口交换控制命令和业务数据。这样可以把实时/低功耗职责和复杂应用职责分开。”

## 12. 大量 IPC 数据为什么常用共享内存？读到一半被写怎么办？

### 面试官原问题

两个进程之间如何通信？为什么控制类消息和大量数据可能使用不同方式？如果共享内存一个进程写、另一个进程读，读到一半的时候被修改怎么办？

### 我当时的回答

我回答控制类消息可以通过 D-Bus / IPC 中间件一类机制完成，而大量数据会更适合共享内存；控制消息里可以传递共享内存相关的标识/句柄，再由双方访问共享区域。我还联系到小鹏侧 IPC 中间件与共享内存的组合使用。

在继续追问共享内存并发同步时，我提到了“保存当前读到的位置”“通过变量校验读多少”“加锁”等想法，但没有形成清楚的数据一致性模型。

### 复盘判断

**控制面 / 数据面的思路是对的，但共享内存同步机制不扎实。** `[weak] [interview]`

### 当时回答的问题在哪里

共享内存只解决“多个进程访问同一块物理数据，减少额外拷贝”，并不会自动保证读写一致性。真正的问题是生产者什么时候算“写完并提交”、消费者什么时候允许读取，因此需要明确同步协议，而不是单纯记录“读到哪里”。

### 推荐回答

“共享内存适合大量数据，因为双方可以直接访问同一块共享区域，避免通过 socket/管道反复复制大块数据；但共享内存本身不提供同步，所以还需要额外的并发控制。简单场景可以用进程间 mutex / semaphore / condition variable，单生产者单消费者场景也可以设计 ring buffer，用原子 read/write index 标识哪些槽已经完整写入、哪些可以读取。核心是消费者只能看到已经提交完成的数据，不能读到生产者正在修改的半成品。”

# 本场暴露的 3 个核心问题

## 1. C / 嵌入式基础知识稳定性不足

最典型的是把 C 语言值传递回答成 C++ 引用语境，以及 I²C START/STOP、FreeRTOS 等题目没有形成条件反射。这里不需要继续扩充特别多新知识，而是先把高频基础题练到可以在 20~40 秒内稳定回答。

## 2. 项目内容比表达出来的水平更强

TBox MCU/Linux 分工、V853 慢客户端、SPI/UART 选型都有真实经验，但现场经常先讲背景、再猜原因、再补充项目事实，导致信息组织很散。以后应优先采用“先结论，再原因，最后项目例子”的顺序。

## 3. 极端情况与同步机制容易被追问打断

V853 被追问“一直丢怎么办”、共享内存被追问“读到一半被写怎么办”时，都暴露出对边界场景缺少提前准备。项目题不能只准备 happy path，要主动准备性能瓶颈、资源耗尽、并发、错误恢复和长期拥塞等极端场景。
