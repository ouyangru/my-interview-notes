## 问题记录

### 1. C 语言函数参数到底是值传递还是引用传递？

**我当时的回答：** 一开始按 C++ 的思路回答成“要看声明，如果用了引用符号就是引用传递”。

**复盘判断：** 答错，但后续对指针和二级指针的行为理解正确。

**状态标记：** `[weak]`

**历史标记：** `[interview]` `[wrong]`

**更好的回答：** C 语言只有值传递。即使参数是 `int *p`，传进去的也是指针值的一份拷贝，所以函数内部执行 `p = NULL` 不会修改调用者保存的那个指针；如果想修改调用者的指针变量本身，需要传 `int **`，然后修改 `*p`。

**继续追问：**

- 修改指针指向的对象为什么只需要 `T *`？
- 修改指针变量本身为什么需要 `T **`？
- C++ 引用与 C 指针参数的语义区别是什么？

### 2. 函数内部定义一个很大的局部数组会怎么样？

**我当时的回答：** 知道非 static 局部变量通常位于栈上、函数结束后生命周期结束，但没有第一时间说到核心风险。

**复盘判断：** 不完整。

**状态标记：** `[weak]`

**历史标记：** `[interview]`

**更好的回答：** 非 static 的大局部数组通常分配在线程栈上，而线程栈大小有限，因此数组过大可能直接导致栈溢出。对于大块动态数据通常应该根据生命周期选择堆分配或其他更合适的存储方式，而不是无条件放在栈上。

---

### 3. `char + int` 的结构体为什么 `sizeof` 可能是 8？

**我当时的回答：** 知道存在内存对齐和 padding，也想到了 `#pragma pack`，但表达比较犹豫。

**复盘判断：** 基本正确但不够稳定。

**状态标记：** `[learning]`

**历史标记：** `[interview]`

**更好的回答：** 如果 `int` 按 4 字节对齐，`char` 占 1 字节后通常需要补 3 字节，再存放 4 字节的 `int`，因此结构体大小通常为 8。`#pragma pack` 可以改变对齐规则、减少 padding，但并不等价于“无条件优化”，因为非对齐访问可能降低性能，某些架构上甚至会受硬件限制。

---

### 4. TCP 为什么是三次握手，而不是两次或四次？

**我当时的回答：** 能解释客户端 SYN、服务端 SYN+ACK、客户端 ACK，也提到服务端可以把 ACK 和自己的 SYN 合并，但表达偏绕。

**复盘判断：** 基本正确。

**状态标记：** `[learning]`

**历史标记：** `[interview]`

**更好的回答：** 三次握手的核心是让双方都确认发送和接收链路正常，并同步双方的初始序列号。两次握手时，服务端无法确认自己的 SYN 是否已经被客户端收到；四次在逻辑上可以工作，但服务端对客户端 SYN 的 ACK 和服务端自己的 SYN 可以合并成同一个报文，因此通常是三次。

---

### 5. TCP 为什么通常需要四次挥手？

**我当时的回答：** 能说明客户端发送 FIN 后，服务端可能仍有数据没有发送完，因此 ACK 和服务端自己的 FIN 不一定能够合并。

**复盘判断：** 基本正确。

**状态标记：** `[mastered]`

**历史标记：** `[interview]`

---

### 6. CAN ID 是干什么的？为什么 ID 越小优先级越高？

**我当时的回答：** 把 CAN ID 说成“主要用于区分不同节点”，后半段知道仲裁时更小 ID 通常拥有更高优先级。

**复盘判断：** 不完整，概念有偏差。

**状态标记：** `[weak]`

**历史标记：** `[interview]`

**更好的回答：** CAN ID 更主要的是标识一类报文及其优先级，而不是简单表示“发送节点是谁”。多个节点同时发送时会进行逐位仲裁，显性位会覆盖隐性位，因此在其他条件一致时数值更小的 ID 通常先赢得总线，仲裁失败的节点停止本次发送并等待后续机会。

---

### 7. I²C、UART、SPI 有什么区别？为什么不同 TBox 平台会选不同接口？

**我当时的回答：** 对 I²C 只记得两根线，对 UART / SPI 的差异和项目选型说得比较散；结合恒润使用 SPI、小鹏部分链路使用 UART 做了一些经验解释。

**复盘判断：** 硬件接口基础明显薄弱，但项目观察本身有价值。

**状态标记：** `[weak]`

**历史标记：** `[interview]`

**更好的回答：** UART 是异步点对点通信，典型使用 TX/RX，通过双方约定波特率工作；I²C 使用 SDA/SCL 两根线，支持地址寻址和一条总线连接多个从设备；SPI 通常使用 SCLK/MOSI/MISO/CS，同步、全双工、吞吐较高，但信号线更多。实际选型需要综合考虑吞吐、实时性、硬件资源、拓扑、协议复杂度以及历史平台方案。恒润和小鹏出现 SPI/UART 差异，并不能只用一个指标解释。

**必须补熟：** I²C 的 START 是 SCL 为高时 SDA 从高变低，STOP 是 SCL 为高时 SDA 从低变高。

### 8. 为什么 Bootloader 往往要分阶段？

**我当时的回答：** 从 x86 启动扇区只有 512 B 出发，解释第一阶段先做最小初始化，再加载更完整的第二阶段；也联系到了实际 SoC 的多阶段启动。

**复盘判断：** 大方向正确。

**状态标记：** `[learning]`

**历史标记：** `[interview]` `[project]`

**更好的回答：** 启动早期通常受到 ROM/启动介质读取方式、可执行空间和硬件初始化状态等限制，因此第一阶段只完成最小硬件初始化与后续镜像加载，再把功能更完整的第二阶段 Bootloader 搬到可用内存执行，后者再负责 DDR、设备初始化、镜像校验以及内核加载等更复杂工作。

### 9. 有时间片以后，为什么还要优先级？FreeRTOS 怎么做调度？

**我当时的回答：** 能想到不同任务的紧急程度不同，但对调度机制和 FreeRTOS 本身不熟。

**复盘判断：** 不完整 / FreeRTOS 基本不会。

**状态标记：** `[weak]`

**历史标记：** `[interview]`

**更好的回答：** 时间片解决的是同优先级任务之间如何公平分享 CPU，而优先级解决的是不同任务的重要性和时效性。以典型抢占式 RTOS 为例，更高优先级的就绪任务可以抢占低优先级任务；同优先级任务之间可以再使用时间片轮转。后续需要补 FreeRTOS 的 task、priority、preemption、queue、semaphore、mutex、ISR 与 task 通信。

### 10. V853 项目里为什么要处理慢客户端？

**我当时的回答：** 采集线程持续产生视频帧，如果某个客户端网络速度很慢，不能让它反向阻塞媒体采集和其他客户端，因此每个客户端维护自己的发送队列，通过 epoll 的可写事件继续异步发送。

**复盘判断：** 这是本场值得保留的项目回答，设计动机是清楚的。

**状态标记：** `[mastered]`

**历史标记：** `[interview]` `[project]`

**更好的展开方式：**

1. **问题：** 视频生产速度可能长期高于某个客户端的发送速度，如果直接同步 `send()`，慢客户端会拖住采集与其他客户端。
2. **设计：** 采集和发送解耦，每个客户端维护独立发送队列；socket 可写时再继续发送。
3. **Trade-off：** 队列不能无限增长，否则内存和观看延迟都会持续增加，因此限制队列长度，在实时预览场景下优先丢旧数据，牺牲部分完整性换低延迟。
4. **极端情况：** 如果客户端长期消费速度低于生产速度，仅靠缓存无法解决，可以继续做降帧率、降码率或直接断开长期拥塞客户端。
5. **编码相关：** MJPEG 每帧相对独立，丢帧影响较小；H.264 存在参考帧依赖，不能简单随机丢帧，严重积压后更合理的是等待新的 IDR / 关键帧重新同步。

**这道题的面试策略：** 项目设计题可以主动按“问题 → 设计 → trade-off → 极端情况”展开，而不是只给一句结论。

### 11. TBox 里的 MCU 和 Linux SoC 分别负责什么？

**我当时的回答：** 能说出 MCU 负责 CAN、外设控制、低功耗唤醒，Linux 侧负责联网、复杂业务和数据存储，但现场表达比较散。

**复盘判断：** 内容有价值，主要问题是组织方式。

**状态标记：** `[learning]`

**历史标记：** `[interview]` `[project]`

**更好的回答：** MCU 更适合承担实时性、低功耗和硬件控制相关任务，例如 CAN 数据采集、部分外设控制，以及 Linux SoC 休眠期间保持运行并负责唤醒；Linux SoC 算力和系统资源更丰富，主要承担 4G/5G 联网、云端协议、复杂业务逻辑和数据存储。两者再通过 SPI/UART 等链路交换控制命令和业务数据。

### 12. 大量进程间数据为什么常用共享内存？如果一个进程读到一半另一个进程又写怎么办？

**我当时的回答：** 知道“控制面可以走 IPC / RPC，大块数据走共享内存”，但同步部分开始混乱，提到了加锁、指针和读写进度，却没有形成完整模型。

**复盘判断：** 思路正确，但同步机制不扎实。

**状态标记：** `[weak]`

**历史标记：** `[interview]`

**更好的回答：** 共享内存解决的是避免重复拷贝和高效共享数据，但它本身不解决并发同步，因此需要额外机制保证数据一致性，例如 mutex / semaphore / condition variable，或者针对单生产者单消费者场景使用 ring buffer + 原子读写索引。核心目标是让消费者只能看到“已经完整提交”的数据，而不是生产者正在修改中的半成品。

## 本场暴露的问题

这场不是“项目没东西”，而是项目经验明显强于基础知识的稳定程度，主要影响结果的是下面三点：

- **基础知识：** C 语言值传递、CAN ID、I²C/UART/SPI、FreeRTOS、共享内存同步等基础知识有明显不稳定或空缺。
- **项目表达：** 实际经历不少，但 TBox MCU/Linux 分工、SPI/UART 选型等回答容易把背景、猜测和结论混在一起，应该先给结论再展开。
- **沟通与结构：** 经常出现“我觉得可能”“我的理解是”“我再补充一点”等自我修正，导致本来七成正确的答案听起来只有四五成确定性。

## 本场形成的面试回答原则

**知识题收着答，项目题展开答；确定的内容再展开，不确定的内容不要边猜边扩展。**

基础知识题第一轮回答控制在“结论 + 关键原因”，通常 20～40 秒；项目设计题则可以主动说明设计背景、实现方案、权衡和极端场景。面试官继续追问时再进入第二层，这样既能控制回答长度，也能避免主动把自己带到不熟悉的知识点。
